# Carbon Scheduler to Modified Bevy Defer Migration Roadmap

Version: v1

Status: planning only; no implementation is authorized by this document

Repository branch studied: dev-rs-v2

Repository commit studied: 73629285578622cadd6994f0504e923262017f1e

Study date: 2026-08-15

## 1. Decision summary

The safe way to achieve the goal is to move Carbon Scheduler's policy, state, channels, accounting, and lifecycle management into a Rust compatibility runtime developed inside the Bevy Defer fork, while retaining Greenlet as the initial continuation backend.

This is not an incidental implementation preference. It is a compatibility requirement:

- Carbon tasklets may suspend from ordinary synchronous Python call stacks at scheduler.schedule(), scheduler.schedule_remove(), channel.send(), channel.receive(), tasklet.run(), and tasklet.switch().
- Bevy Defer and async-executor suspend only at Rust Future poll boundaries.
- A Future executor cannot suspend an arbitrary synchronous Python stack without a stackful continuation mechanism or a source transformation of every caller.
- Carbon also supports immediate exception injection into a suspended tasklet, parent-chain switching, synchronous rendezvous channels, nested run boundaries, and exact queue-position rules. None of those semantics are supplied by LocalExecutor::try_tick().

Therefore the migration must use this architecture:

1. Keep the existing Python module and SchedulerCAPI contract unchanged.
2. Keep Greenlet, or a proven equivalent stackful continuation, behind a narrow continuation interface during compatibility migration.
3. Put the new scheduler kernel in the modified Bevy Defer source tree, but make the kernel independent of Bevy ECS and frame execution.
4. Add deterministic tasklet queue primitives. Do not use async-executor's ordinary FIFO runnable queue as the source of Carbon scheduling order.
5. Use the vendored async-executor only after explicitly wiring it into the dependency graph, and only for mechanisms that can preserve Carbon's ordering and lifecycle laws.
6. Run the C++ implementation and Rust implementation behind the same tests and a differential trace oracle until they are behaviorally indistinguishable.
7. Remove C++ scheduling logic only after Python, C ABI, ordering, exception, threading, reference-lifetime, and teardown gates all pass.

The migration should not begin as a pure async/await rewrite. That would silently change the programming model and would not be a reimplementation of the existing Carbon Scheduler contract.

## 2. Planning contract

### 2.1 In scope

- Reimplement the behavior currently owned by ScheduleManager, Tasklet, Channel, and their Python wrappers.
- Preserve the public scheduler package, the _scheduler extension module, Python types, methods, properties, exceptions, callbacks, iteration behavior, and documented scheduling controls.
- Preserve the SchedulerCAPI capsule name, table layout, function pointer order, signatures, type pointers, exception pointer, reference ownership, and GIL expectations.
- Modify the Bevy Defer fork to host a deterministic, host-independent Carbon compatibility runtime.
- Modify or wrap the vendored async-executor when a low-level runnable or wake mechanism is useful and can be made deterministic.
- Preserve Greenlet initially as the continuation engine.
- Preserve current Windows and macOS build targets and Python 3.12-era behavior.
- Add a staged build integration between Cargo and the existing CMake/vcpkg project.
- Add characterization, property, differential, concurrency, ABI, memory, and teardown tests before switching production behavior.

### 2.2 Out of scope for this version

- No production source code is to be written as part of v1.
- No current tests are to be weakened, deleted, skipped, or rewritten around new implementation details.
- No public API cleanup, spelling cleanup, field rename, callback signature change, or C capsule reordering is bundled into the migration.
- No automatic conversion of synchronous Python tasklet bodies to async Python or Rust Futures.
- No removal of Greenlet before a separate proposal proves an equivalent stackful mechanism against the complete oracle.
- No default change from nested scheduling to flat scheduling.
- No dependency on a Bevy App, World, ECS schedule, render loop, or frame clock in the compatibility kernel.
- No attempt to reproduce apparent implementation defects merely because they exist in a code block. Observable, tested behavior is the contract; suspicious behavior must first be characterized.
- No migration of unrelated vcpkg registry payload, artwork, licenses, or generated documentation infrastructure.

### 2.3 Compatibility authority

Use this order when sources disagree:

1. Existing Python and C API tests.
2. Reproducible behavior of the baseline extension at the pinned commit.
3. The public C header and exported Python surface.
4. User-facing documentation.
5. Comments and internal implementation details.

Do not treat an internal bug as an intentional law until a test, an external consumer, or a deliberate compatibility decision establishes it.

Channels are iterators. Iteration repeatedly receives; it stops only when the channel is closed. A normal open channel does not use StopIteration as an empty-queue signal.

The scheduler package additionally exposes QueueChannel and block_trap:

The current QueueChannel creates a fresh threading.Lock inside each operation. That does not provide shared mutual exclusion. Do not reproduce that detail in Rust unless a characterization test demonstrates an externally visible dependency.

### 4.5 Per-thread scheduler laws

Each Python thread lazily acquires one ScheduleManager through its Python thread-state dictionary under SCHEDULE_MANAGER.

The manager:

- Creates a main tasklet wrapping the thread's current Greenlet.
- Tracks main, current, queue tail, switch-trap level, run mode, limits, counters, and all tasklets associated with that thread.
- Uses a closing-manager map during destruction to prevent cleanup code from accidentally creating a replacement manager for the same dying thread.
- Treats the main tasklet as part of reported run-count behavior.
- Owns the strong reference for each runnable queue membership.
- Preserves a current/parent relationship so nested tasklets return to the correct continuation.

The new implementation must keep manager identity tied to Python thread state, not merely an operating-system thread-local variable. Python subinterpreter and thread-state behavior must be characterized before changing the storage mechanism.

### 4.6 Runnable queue laws

The current queue is deterministic and intrusive. Observable laws include:

- Normal insertion appends to the back.
- A new valid tasklet becomes runnable.
- remove detaches a runnable tasklet and makes it paused while preserving liveness.
- insert reattaches a valid paused tasklet at the back.
- schedule yields and requests reinsertion at the back.
- schedule_remove yields without normal reinsertion and preserves the special tagged-removal behavior.
- tasklet.switch transfers immediately without applying the same queue traversal as a normal run.
- tasklet.run starts at a selected tasklet and applies either nested or flat behavior.
- FRONT_PLUS_ONE reinsertion preserves the task already at the front, then places the yielding tasklet immediately after it.
- The next and prev properties reflect actual queue linkage; detached or blocked tasklets expose the tested null behavior.
- The schedule callback observes each actual current-tasklet transition with exact previous and next objects.

Nested scheduling is enabled by default. Under nested behavior, a run from a tasklet sets a boundary at the queue tail that existed at entry. Tasklets added during that bounded run remain for a later run. A scheduler.run from main has different reach and processes newly appended work until the queue is exhausted.

Flat mode is a supported alternate contract, not permission to remove nested mode. It changes tasklet.run so only the selected tasklet is moved for immediate execution and the rest of the queue remains flat.

The implementation must model run boundaries explicitly. A generic drain-until-empty loop cannot represent both behaviors.

### 4.7 Run-budget laws

run_n_tasklets and C API run-with-timeout are not simple wrappers around an asynchronous executor:

- Tasklet limits are checked in the current implementation at main-tasklet scheduling boundaries when nested mode is active.
- Time limits are measured with a monotonic clock.
- A zero or already-expired timeout still permits at least one tasklet to make progress.
- Timeout counters distinguish completed tasklets from attempted switches.
- The attempted-switch counter may increase even when switch_trap prevents the switch.
- Limit state is reset after the run, including error paths.
- When main is blocked on a channel, the run loop continues until main becomes unblocked or a deadlock is established.

These details need direct oracle tests before implementation because comments and documentation acknowledge nested-mode limitations.

### 4.8 Tasklet state and continuation laws

The existing Tasklet class combines several concerns that should be separated in Rust:

- Python object ownership and GC integration.
- Greenlet continuation ownership.
- Runnable queue membership.
- Channel wait-list membership.
- Thread ownership.
- Parent continuation.
- Callable and argument binding.
- Transfer values and exception triples.
- Pending control requests.
- Telemetry metadata.

Externally observable laws include:

- A tasklet may be unbound, newly runnable, running, paused, blocked, or dead.
- A tasklet cannot be both runnable and blocked.
- blocked implies association with a channel and direction.
- scheduled reports the repository's tested meaning, including blocked tasklets where applicable.
- A current tasklet is thread-local.
- Main is alive and current at manager creation.
- Rebinding resets execution state and times_switched_to as tested.
- Immediate kill or throw may transfer control now; pending kill or throw schedules delivery and lets the caller continue.
- TaskletExit has special handling on new, running, blocked, paused, and already-dead tasklets.
- Killing or throwing into a channel-blocked tasklet must unlink it from the correct channel FIFO and update balance and close state exactly once.
- A blocked tasklet cannot be resumed by an unrelated ordinary queue operation.
- A parent that is blocked is skipped when choosing a safe return continuation; dead parent links must not be dereferenced.
- switch_trap and block_trap reject control transfer before mutating queue or channel accounting.
- Cross-thread operations follow existing success, error, or no-op rules; they are not uniformly permitted.
- dont_raise, context_manager_getter, and exception_handler alter uncaught-exception handling without changing scheduler invariants.

### 4.9 Channel laws

Carbon channels are synchronous rendezvous channels, not buffered event streams.

They maintain two independent FIFO wait queues:

- Waiting senders.
- Waiting receivers.

Balance is signed:

- Positive values count waiting senders.
- Negative values count waiting receivers.
- Zero means no unmatched waiters.

A send with no waiting receiver blocks the sender. A receive with no waiting sender blocks the receiver. When a counterpart exists, exactly one sender and one receiver are matched in FIFO order and one transfer packet moves from sender to receiver.

A transfer packet must represent either:

- A normal Python value.
- An exception class or instance plus arguments.
- A throw triple consisting of exception, value, and traceback, with restore semantics.
- A pending TaskletExit/control condition.

Preference is clamped to sender, receiver, or neither and controls who continues immediately after a successful rendezvous:

- Receiver preference is represented by -1.
- Neither is represented by 0.
- Sender preference is represented by 1.

The exact observed execution order for all three values must remain test-driven. Preference affects scheduling after a transfer; it does not change FIFO counterpart selection.

Other channel laws:

- The global channel callback runs once per send or receive attempt with channel, current tasklet, is_sending, and will_block.
- A block-trapped operation that would block raises before changing balance or wait queues.
- close enters closing while waiters remain and closed when the channel becomes empty.
- open resets close state.
- send or receive on a closed channel raises the established error.
- clear terminates blocked tasklets using the established immediate/pending behavior.
- unblock_all_channels visits the global active-channel set and preserves return-count behavior.
- Cross-thread rendezvous inserts the released tasklet into its owning scheduler, not the caller's scheduler.
- Removing a blocked tasklet because of kill, throw, clear, or thread teardown updates links, ownership, balance, and closing state atomically.

Bevy Defer's Event and oneshot utilities do not satisfy this contract. Event is buffered and consumes queued items independently of tasklet scheduling. The oneshot is single-use and has Future/waker cancellation semantics. They may supply implementation ideas, but neither can replace Channel directly.

### 4.10 Callbacks, counters, and lifetime laws

The following are compatibility surfaces:

- Python schedule callback: global across managers and returns the previous callback from the setter.
- Fast C schedule callback: a direct function pointer invoked without a Python call wrapper.
- Python channel callback: global across channels and returns the previous callback from the setter.
- Active schedule-manager count.
- Active channel count.
- All-time tasklet count.
- Active Python tasklet-object count, regardless of alive/dead execution state.
- Per-time-limited-run completed and attempted-switch counters.
- Tasklet timestamps, total runtime, context text, parent callsite, method/module/file/line metadata, highlighted marker, and times_switched_to.

Every pointer passed to a callback must remain alive for the duration of the callback. Callback reentrancy must be characterized: callbacks can execute Python and may inspect or attempt to mutate scheduler state.

Queue ownership, channel ownership, parent ownership, Python wrapper ownership, Greenlet ownership, callable/argument ownership, transfer ownership, callback ownership, and exception ownership need an explicit reference ledger. Rust memory safety does not automatically make Python reference-count behavior compatible.

## 5. What the Bevy Defer study establishes

### 5.1 Reusable concepts

| Bevy Defer area | Current behavior | Appropriate migration use |
|---|---|---|
| executor.rs | Stores a non-send LocalExecutor resource and pumps it with repeated try_tick while scoped thread-local world resources are active | Reuse the idea of an explicitly scoped execution context and a single host-thread pump |
| spawn.rs | Uses scoped thread-local spawner access and task handles, with state-scoped cancellation by dropping handles | Reuse bounded spawn/context APIs for auxiliary Rust async work; do not map Tasklet lifetime directly to Task handle lifetime |

| commands.rs | Provides synchronous access to scoped World state and Future helpers | Keep behind Bevy-specific features; never require World access to run Carbon |
| cancellation.rs | Provides cooperative cancellation tokens checked by participating routines | Reuse only for auxiliary futures; Carbon kill/throw requires continuation-level delivery |
| sync/oneshot.rs | A local Rc-based one-shot channel with drop cancellation and wakers | Reuse patterns for FFI completion signals, not as Carbon Channel |
| event.rs | Buffered VecDeque plus event notification | Reuse for telemetry/event delivery, not rendezvous semantics |
| async_shared | Watch-style last-value synchronization | Keep independent; do not use as a tasklet transfer channel |
| signals and reactors | Type-erased watch registration for Bevy state, components, and messages | Keep in the optional Bevy bridge |

| derive | Generates Bevy access traits and dynamic access adapters | No role in scheduler compatibility |

### 5.2 Bevy Defer constraints

- AsyncExecutor is a Bevy non-send resource wrapping Rc<LocalExecutor<'static>>.
- The executor is pumped only while scoped thread-local references to the Bevy World and auxiliary queues are installed.
- run_async_executor drains currently runnable Futures by calling try_tick repeatedly.
- with_world_ref and with_world_mut panic outside the scoped pump and guard nested mutable access.
- yield_now is a Future that registers a waker and becomes ready on a later executor frame.
- Cancellation is cooperative and Future-oriented.
- State-scoped task cancellation occurs through handle drop.
- Bevy time, frame, state, message, component, asset, and scene facilities are host concerns, not Carbon scheduler laws.

The Carbon kernel must therefore be extracted behind a feature and API boundary that has no bevy::World type in its public or private core state.

### 5.3 Observed Bevy Defer drift to quarantine

The study found several suspicious or stale areas that must not be copied into the compatibility kernel without tests:

- The package version and README compatibility table are not aligned.
- The http subcrate declares an older Bevy Defer version and a Bevy version different from the root.
- async_shared::Value has a write_if_changed implementation whose condition appears inverted relative to its name.
- Signal receiver initialization appears to write into the sender map in one path.
- The local async-executor copy is not wired into the root dependency graph.

These are review findings, not migration requirements. Isolate the new scheduler feature from them.

## 6. What the async-executor study establishes

### 6.1 Current executor mechanics

The vendored async-executor 1.14.0 implementation:

- Lazily allocates shared State behind an atomic pointer.
- Stores scheduled Runnable values in a global ConcurrentQueue.
- Tracks active tasks in a Slab of Wakers.
- Uses async-task to build tasks with panic propagation.
- Schedules a woken task by pushing its Runnable onto a queue and notifying a sleeper.
- Makes LocalExecutor non-Send and non-Sync while sharing the same underlying state design.
- Implements try_tick by popping one runnable from the global queue and polling it once.
- Implements run with a Runner, a bounded local queue, random queue selection, stealing, fairness logic, and sleeper notification.
- Wakes active tasks and drains queued runnables during executor drop.
- Uses Task handle semantics in which cancellation and detach behavior differ from Carbon's Python-object and queue-reference lifetime.

The local Bevy Defer driver uses try_tick, not run. Therefore its practical behavior is one global FIFO runnable poll at a time until the queue is temporarily empty.

### 6.2 Why the current executor cannot be the Carbon queue

| Carbon requirement | Current async-executor behavior | Required change |
|---|---|---|
| Insert at back | Global FIFO enqueue | Can be represented, but only if no other wake source changes order |
| Insert immediately after protected front | No public position-aware enqueue | Add an explicit deterministic scheduling policy or a separate tasklet queue |
| Remove an arbitrary runnable tasklet | Task cancellation is not queue detachment and pause | Add stable task identity and removable queue membership |
| Paused but alive tasklet | Dropped/cancelled Future is not paused stackful execution | Keep continuation state separate from Future Task |
| Immediate switch | One Future poll cannot transfer an arbitrary Python stack | Use continuation backend directly |
| Pending throw/kill | Future cancellation cannot inject a Python exception at suspension | Add explicit control packet delivered on continuation resume |
| Nested run boundary | drain-until-empty has no entry-tail snapshot | Add run epochs/boundary tokens |
| Exact callback pair per current transition | Waker scheduling is not tasklet switching | Emit callbacks in scheduler transition logic |
| Cross-thread channel release into owner queue | Shared executor scheduling lacks Python thread ownership semantics | Route by manager identity and wake the owning host |
| Stable deterministic order | run includes random/local/steal behavior; wake order can vary | Do not use run/Runner for compatibility execution |
| Queue-owned reference | Runnable and Task ownership follow async-task rules | Define an independent Python/Rust reference ledger |

### 6.3 Permitted async-executor role

There are two acceptable designs:

1. Preferred: keep the Carbon tasklet queue as a dedicated deterministic queue in the Bevy Defer fork. Use async-executor only for auxiliary Rust Futures and host wakeups.
2. Conditional: modify async-executor to expose a pluggable deterministic scheduler and explicit runnable handles, then prove that the new path does not use the random runner, local work stealing, implicit duplicate wake ordering, or cancellation semantics for Carbon tasklets.

Do not generalize async-executor before the Carbon laws are encoded. A small dedicated queue is less risky than changing a general-purpose executor and then attempting to recover stackful semantics from it.

| Topic | Carbon Scheduler | Bevy Defer / async-executor | Migration consequence |

|---|---|---|
| Python/C ABI facade | Existing type names, method parsing, properties, errors, capsule, docstrings, GIL entry, Python GC hooks | Scheduling policy |
| FFI bridge | Opaque stable handles, panic containment, reference operations, error conversion, Greenlet calls | Public behavior decisions |
| Carbon compatibility runtime in Bevy Defer fork | Manager registry, TaskletCore, ChannelCore, run controller, callbacks, counters, teardown | Bevy ECS data |
| Deterministic scheduler | Stable task IDs, queue links, enqueue positions, removal, current transitions, run boundaries | Python object parsing |
| Continuation adapter | Create/current/resume/suspend/throw/dead/parent operations | Queue or channel policy |
| Optional Bevy host adapter | Pump compatibility managers from a Bevy schedule and bridge auxiliary Futures | Core tasklet semantics |
| Auxiliary async executor | Non-compatibility Rust Futures, timers, I/O, host wake signals | Canonical Carbon tasklet order |

The dependency direction must point inward. The standalone CPython extension can use the compatibility runtime without initializing Bevy. A Bevy application can opt into the host adapter without changing scheduler behavior.

### 8.2 Recommended crate layout

Keep names provisional until implementation starts, but enforce these dependency boundaries:

- bevy_defer::carbon_core, or a workspace crate consumed by Bevy Defer:
  - scheduler
  - tasklet
  - channel
  - run_scope
  - transfer
  - callback
  - metrics
  - lifecycle
- bevy_defer::carbon_ffi, or a sibling static library:
  - raw CPython/Greenlet bridge
  - exported C-compatible operations
  - panic and error boundary
- bevy_defer::carbon_bevy:
  - optional plugin/resource/system integration
- Existing Bevy Defer modules:
  - remain behind their current features
  - depend on no Carbon public type unless a deliberate adapter requires it
- Vendored async-executor:
  - a pinned path dependency
  - unchanged for Phase 0
  - modified only after a focused design proves the need

### 8.3 Facade migration choice

Use a thin compatibility facade before attempting a native Rust Python type implementation.

Recommended sequence:

1. Keep the current C++ PyTypeObject definitions and Greenlet C API calls.
2. Replace internal scheduling decisions with calls into a Rust static library through a narrow C ABI.
3. Keep PyTaskletObject and PyChannelObject opaque to external consumers as they are today.
4. Keep SchedulerCAPI populated by the same facade functions.
5. Once all gates pass, decide separately whether moving the facade to pyo3-ffi or raw CPython FFI reduces maintenance without changing ABI.

This sequence makes rollback a link-time or feature-flag choice. It also avoids combining scheduler semantics, Python type-layout changes, and a language boundary in one step.

If the project requires zero C++ in the final state, add that as a later facade-only phase. Do not make it a prerequisite for moving scheduler behavior.

## 9. Required internal model

### 9.1 Stable identities

Use opaque, generational identities for managers, tasklets, channels, wait nodes, and run scopes. Never expose a Rust address as a durable Python or C identity.

Each handle must fail closed when:

- Its generation no longer matches.
- Its manager is closing.
- It belongs to a different Python thread for an operation that requires local ownership.
- Its Python wrapper has entered GC clearing/deallocation.

### 9.2 Manager state

Each manager needs:

- Python thread identity and thread-state association.
- Main tasklet ID.
- Current tasklet ID.
- Runnable queue head/tail or sentinel.
- Queue length with a debug recomputation path.
- Switch-trap level.
- Nested-mode setting or access to the current global setting, matching baseline scope.
- Stack of active run scopes.
- Current run mode and budget.
- Stop flag.
- Timeout counters.
- Registered tasklets.
- Closing flag.
- Host wake signal for cross-thread channel releases.

All state mutations must occur through manager operations that validate invariants before and after mutation in debug/test builds.

### 9.3 Tasklet states

Represent state explicitly instead of relying on independent booleans that can form impossible combinations.

| Canonical state | Meaning | Queue membership | Channel membership | Continuation |
|---|---|---|---|---|
| Unbound | No executable callable/arguments | None | None | Absent or reset |
| Ready | Runnable and waiting | Exactly one manager queue | None | Created or resumable |
| Running | Current tasklet | Not a waiting queue node | None | Active |
| Paused | Alive but deliberately detached | None | None | Suspended |
| BlockedSend | Waiting to rendezvous as sender | None | Exactly one send FIFO | Suspended |
| BlockedReceive | Waiting to rendezvous as receiver | None | Exactly one receive FIFO | Suspended |
| Dead | Completed or terminated | None | None | Dead |

Main is a distinguished tasklet whose valid state transitions differ from ordinary tasklets.

Keep orthogonal fields only where they are genuinely orthogonal:

- block_trap
- pending control packet
- transfer packet
- tagged-removal behavior
- reschedule request
- parent tasklet
- thread/manager
- metadata
- dont_raise/context-manager/handler policy

Derive alive, blocked, scheduled, paused, is_current, and is_main from canonical state plus manager identity. Add assertions that the derived values match the baseline oracle.

### 9.4 Tasklet transition table

| Operation | Allowed source | Target/effect | Required checks |
|---|---|---|---|
| construct/bind/setup | Unbound or tested rebindable dead state | Ready | Callable validity, arguments, thread ownership, metadata reset |
| insert | Paused or valid detached state | Ready at back | Same owner thread where required; no duplicate membership |
| remove | Ready | Paused | Release exactly one queue-owned reference |
| schedule | Running | Ready at back after returning to parent | switch_trap, parent validity, callback order |
| schedule_remove | Running | Paused/tagged path | Preserve liveness and tested reinsertion behavior |
| tasklet.run nested | Ready/Paused as tests permit | Running in bounded scope | Set parent, entry-tail boundary, direct target selection |
| tasklet.run flat | Ready/Paused as tests permit | Running then flat queue restoration | FRONT_PLUS_ONE behavior |
| tasklet.switch | Valid target | Immediate Running target | switch_trap, blocked/dead/thread rules |
| channel unmatched send | Running | BlockedSend | block_trap before balance mutation |
| channel unmatched receive | Running | BlockedReceive | block_trap before balance mutation |
| channel match | Blocked counterpart plus Running caller | Transfer and preference-dependent Ready/Running states | FIFO, owner manager routing, one balance update |
| pending throw/kill | Alive valid target | Same state plus pending control | Do not switch immediately |
| immediate throw/kill | Alive valid target | Running for delivery, then Ready/Paused/Dead per outcome | Unlink blocked target first, parent safety |
| normal completion | Running | Dead | Remove memberships, set end/runtime, propagate or handle result |
| thread shutdown | Any owned non-main tasklet | Dead or deliberately leaked only under documented last-resort policy | No manager recreation; bounded cleanup decision |

Every invalid transition needs the exact Python exception type and message established by baseline tests.

### 9.5 Deterministic queue API

The compatibility runtime needs semantic operations, not a generic push/pop abstraction:

- enqueue_back(tasklet)
- enqueue_run_next(tasklet)
- enqueue_front_plus_one(tasklet)
- remove_ready(tasklet)
- peek_next_after(base)
- begin_run_scope(start, boundary_kind)
- advance_run_scope(scope)
- end_run_scope(scope)
- set_current(next)
- recompute_count()

Queue operations must:

- Reject duplicate insertion.
- Hold exactly one queue ownership reference.
- Clear channel membership before insertion.
- Maintain next/prev observations.
- Update the cached count exactly once.
- Emit no callback by themselves unless current changes.
- Be deterministic under callback reentrancy.

### 9.6 Run scopes

A RunScope records:

- Entry current/parent tasklet.
- Starting base position.
- Boundary tasklet or unbounded-main mode.
- Nested versus flat mode.
- Standard, task-count, time-count, or unblock-main objective.
- Remaining tasklet budget.
- Deadline and first-progress allowance.
- Completed and attempted-switch deltas.
- Stop/error outcome.

Do not keep run-budget fields as ambient mutable globals when nested runs can occur. A scope stack makes restoration explicit and prevents an inner run from corrupting an outer run's limit.

### 9.7 Transfer and control packets

Use separate tagged representations:

- Value transfer.
- Exception plus arguments.
- Restored throw triple.
- Pending kill.
- Pending throw.
- Internal wake without data.

At the FFI boundary, every packet documents whether each PyObject pointer is borrowed, newly owned, or stolen. A packet destructor must run with the GIL and release each owned reference exactly once.

Do not overload null pointers to represent multiple meanings.

### 9.8 Channel synchronization

Channels can be used across Python threads, so their waiter queues need a synchronization strategy independent of the GIL assumption.

Recommended design:

- Protect channel state and both waiter FIFOs with one mutex.
- Keep critical sections small and never switch Greenlets or invoke Python callbacks while holding the mutex.
- Under the lock, validate state, select/unlink a counterpart, update balance/close state, and create an immutable rendezvous action.
- Release the lock.
- Route the action to the owner manager of each affected tasklet.
- Acquire the GIL and perform Python reference/control work in a defined order.
- Wake the owning host thread if it is not the caller.

Specify a total Rust-lock order before implementation:

1. Global registry lock.
2. Channel lock.
3. Manager lock or manager command queue.

Python entry points normally already hold the GIL, so the GIL is not another freely reorderable Rust lock. No thread holding a Rust lock may wait to acquire the GIL, invoke Python, or switch a continuation. A GIL-holding entry point may take a Rust lock only because every non-GIL holder is required to release that lock without waiting for the GIL. The exact Rust-lock order may be revised after a lock audit, but recursive acquisition must be prohibited and tested.

### 11.2 Invariants for property tests

At every observable boundary:

- Exactly one current tasklet exists per live manager.
- Main belongs to its manager and is never in a channel wait queue.
- A non-dead tasklet has at most one queue/channel membership.
- Ready tasklets are present exactly once in their manager queue.
- Blocked tasklets are present exactly once in one channel direction queue.
- Queue next/prev links are reciprocal.
- Channel next/prev blocked links are reciprocal.
- Cached runnable count equals recomputed count.
- Channel balance equals sender count minus receiver count, using the repository's sign convention.

- A tasklet manager/thread does not change after binding except through an explicitly tested reset path.

- A run scope restores the outer current, mode, budget, and boundary on every exit.
- Each successful rendezvous transfers exactly one packet.
- Each current transition emits the expected callback at most once.
- Pending control is delivered at most once.
- Cross-thread release targets the tasklet owner's manager.
- No Rust panic crosses into C or Python.

## 12. Performance plan

Behavioral parity comes first. After parity:

Measure representative distributions, not only microbenchmarks:

- Queue insert/remove/run-next/front-plus-one latency.
- Greenlet switch and return latency.
- scheduler.run throughput for short and long tasklets.
- Timeout overshoot.
- Channel rendezvous latency for same-thread and cross-thread pairs.
- Contended channel throughput.
- Cost of callbacks enabled and disabled.
- Manager/tasklet/channel memory.
- Allocation count per yield and rendezvous.
- Thread-exit cleanup time.
- Bevy frame-pump budget when the optional adapter is enabled.

Initial acceptance budget should be agreed from baseline measurements. A reasonable provisional rule is no more than 10% regression in median tasklet switch/rendezvous throughput and no more than 20% regression at p99, unless a measured safety improvement justifies it. Memory must remain bounded under long-running property and stress tests.

Do not optimize by:

- Reordering callbacks.
- Batching tasklet transitions invisibly.
- Dropping queue ownership.
- Replacing FIFO with work stealing.
- Deferring Python decrefs to an unsafe thread.
- Removing invariant checks before measurement.

## 13. FFI, safety, and ownership requirements

### 13.1 FFI rules

- Every extern function is panic-contained.
- Every raw pointer is checked for null, type, liveness, and generation where possible.
- No Rust reference outlives the GIL-protected Python object access from which it came.
- No Python C API call occurs without the GIL.
- No Greenlet switch occurs from the wrong thread.
- No mutex guard lives across a Greenlet switch, Python callback, or arbitrary Python call.
- Error paths initialize a Python exception before returning a null pointer or error status.
- Success paths do not leave a stale Python exception.
- Callback failures follow baseline propagation and cleanup.

### 13.2 Ownership ledger

Before each phase is approved, document these edges:

| Owner | Object/reference | Acquisition | Release |
|---|---|---|---|
| Python wrapper | Rust handle or legacy implementation pointer | tp_new/tp_init | tp_clear/tp_dealloc |
| TaskletCore | callable, args, kwargs, Greenlet, handlers, metadata objects | bind/setup/create | rebind/clear/death/dealloc |
| Manager queue | ready tasklet | enqueue | remove/dequeue/death/close |
| Channel wait FIFO | blocked tasklet and transfer packet | unmatched send/receive | match/kill/throw/clear/close/teardown |
| Parent relation | parent tasklet where baseline uses strong ownership | run/switch parent set | return/death/reparent |
| Global callback slot | Python callable | setter | replacement/module teardown |
| C API capsule | type and exception pointers | module initialization | module finalization process |
| Cross-thread command | tasklet/channel/packet handles | routing | consumption/rejection |

The implementation review must show that every edge has one acquisition and one release on every success and failure path.

### 13.3 Unsafe-code policy

Concentrate unsafe code in:

- CPython type/capsule facade.
- Greenlet adapter.
- Handle conversion.
- C callback invocation.

The scheduler, queue, state machine, run scopes, and channel selection logic should remain safe Rust. Add safety comments that state the caller obligations and prove them at the boundary.

## 16. Risks and decisions that must be explicit

### 16.1 Greenlet retention

Recommendation: retain Greenlet through behavioral switchover.

Falsifier: a replacement demonstrates suspension of arbitrary synchronous Python stacks, immediate and pending exception injection, parent switching, thread affinity, refcount behavior, and every differential oracle case without call-site transformation.

### 16.2 Bevy coupling

Recommendation: host the runtime in the Bevy Defer fork but keep carbon_core Bevy-free.

Falsifier: a product requirement proves all scheduler consumers already run inside one Bevy World and no standalone Python/C API consumer exists. Even then, ABI tests remain mandatory.

### 16.3 async-executor modification

Recommendation: wire and pin the fork, but prefer a separate deterministic tasklet queue.

Falsifier: a focused prototype proves that a small scheduler hook in async-executor represents every queue position, arbitrary removal/pause, nested boundary, owner-thread route, callback point, and rollback requirement with less code and equal isolation.

### 16.4 Nested scheduling

Recommendation: preserve nested mode and its current default.

Falsifier: product owners explicitly approve a compatibility break after telemetry proves no dependency and migration notes cover ordering changes. That is a separate project decision.

### 16.5 C++ facade

Recommendation: keep a minimal facade through the first Rust production release.

Falsifier: a Rust-native facade passes byte-level capsule layout, external consumer, Python type/GC/subclassing, Greenlet, and rollback gates before scheduler logic moves.

### 16.6 Subinterpreters and free-threaded Python

The current extension uses global module state and global callbacks and is not designed as a modern per-interpreter module. Do not promise subinterpreter isolation or free-threaded Python support as part of compatibility. First characterize current behavior. A future support project can deliberately change the module-state model.

### 16.7 Teardown that catches TaskletExit

The current comments acknowledge potentially unbounded cleanup if user code repeatedly catches termination. The replacement needs an explicit bounded policy. Preserve ordinary behavior, but do not create an infinite destructor loop. Decide among a bounded retry plus leak, a fatal diagnostic in debug, or another product-approved policy, and test it.

### 16.8 Apparent baseline defects

Potential defects observed during study must enter a decision log rather than silently becoming Rust behavior:

- QueueChannel's per-call lock.
- get_thread_info run-count arithmetic if characterization confirms double addition.
- callback null assumptions and callback-error handling.
- suspicious reference-count branches.
- Bevy Defer signal/shared-value issues.
- documentation inconsistencies.

For each, choose one:

- Preserve because an external compatibility test requires it.
- Fix before migration in an isolated legacy change with a regression test.
- Fix identically in old and new implementations during dual-run.
- Leave unsupported and document the exact boundary.

## 17. Definition of done

The goal is complete only when all of the following are true:

- The modified Bevy Defer fork contains the authoritative Carbon scheduler, tasklet state, channel, run-scope, callback, metric, and lifecycle logic.
- The core runs without Bevy.
- Greenlet remains behind a replaceable continuation interface, or a separately approved equivalent has passed all gates.
- The vendored async-executor selection is proven and reproducible.
- Every existing Python test passes unchanged under the Rust implementation.
- Every existing C API test passes unchanged under the Rust implementation.
- An external consumer compiled with the unchanged Scheduler.h imports and uses scheduler._C_API successfully.
- Nested and flat scheduling traces match the baseline.
- Channel FIFO, preference, balance, cross-thread, close/open/clear, exception transfer, and callback traces match.
- Immediate and pending kill/throw behavior matches in every tasklet state.
- Thread creation/destruction, interpreter teardown, GC cycles, weakrefs, and refcounts meet the baseline without new leaks or crashes.
- No Rust panic crosses FFI.
- No data race, deadlock, lost wake, duplicate membership, count drift, or stale handle is found by the required tests.
- Supported platform builds and package contents match.
- Performance remains within the approved budgets.
- The Rust implementation has completed an opt-in period, default-on period, and tested rollback window.
- Documentation describes the implementation that actually ships.
- Removal of legacy C++ logic receives separate approval after rollback evidence is retained.

## 18. First implementation work package

When code work is authorized, the first pull request should contain only:

1. Dependency wiring that proves the local async-executor fork is selected.
2. A pinned Rust toolchain and reproducible lockfile decision.
3. CMake/Cargo build integration with legacy behavior still the default.
4. An empty host-independent Carbon compatibility crate/module boundary.
5. A versioned differential trace schema and legacy trace adapter.
6. Baseline CI entries for legacy, Rust-core-unit, and dependency-graph verification.
7. No scheduler decision moved to Rust.
8. No Python or C API behavior change.

That work package creates the trustworthy foundation for all later phases and can be reverted without affecting users.

## 19. Prohibited shortcuts

- Do not replace tasklets with spawned Futures and call the migration complete.
- Do not equate one try_tick poll with one Carbon tasklet switch.
- Do not use async-executor run or work stealing for compatibility order.
- Do not buffer Carbon channel sends to avoid blocking.
- Do not drop Greenlet before synchronous suspension is solved.
- Do not change nested mode's default.
- Do not reorder or extend SchedulerCAPI in place.
- Do not expose Rust addresses as handles.
- Do not hold Rust locks across Python calls or Greenlet switches.
- Do not perform Python decrefs on an arbitrary Rust worker thread.
- Do not use sleeps as concurrency test synchronization.
- Do not normalize meaningful differential mismatches.
- Do not fix apparent legacy bugs only in the new implementation during parity work.
- Do not switch implementation after runtime objects exist.
- Do not remove the legacy rollback path before the production observation window closes.
- Do not claim the vendored executor is active without Cargo metadata evidence.
- Do not claim configuration is live on a host without an effective-config or bounded role probe.

| async-executor/tests/local_queue.rs | Local queue scheduling/stealing behavior | Must stay out of deterministic Carbon path |
| async-executor/tests/panic_prop.rs | Panic propagation from tasks | FFI still requires an additional panic boundary |
| async-executor/tests/spawn_many.rs | Batch spawn behavior | Auxiliary executor regression only |
| async-executor/examples/limit.rs | Limits concurrency around an executor | Not a tasklet run-budget model |
| async-executor/examples/priority.rs | Implements priority using separate executors | Evidence that current executor has no Carbon queue-position API |
| async-executor/benches/executor.rs | General executor throughput benchmark | Retain upstream signal; add separate Carbon benchmarks |
| async-executor/Cargo.toml | async-task, concurrent-queue, fastrand, futures-lite, slab, and static feature dependencies | Supply-chain and feature audit boundary |

## 21. Final recommendation

Proceed with a compatibility kernel, not a future-only rewrite.

The modified Bevy Defer fork should become the home of a deterministic, host-independent Rust runtime. Carbon tasklets should remain stackful through a Greenlet continuation adapter, while scheduling, channels, state validation, callbacks, counters, cross-thread routing, and teardown move into Rust in small differential phases. async-executor should remain auxiliary unless a narrowly scoped deterministic hook proves it can preserve every Carbon law.

This plan gives the project a real Rust reimplementation, retains the behavior that existing Python and C consumers depend on, keeps Bevy integration optional, and preserves a practical rollback at every step.
