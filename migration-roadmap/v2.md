## 1. Decision summary

The goal remains to reimplement Carbon Scheduler by modifying the Bevy Defer fork, while preserving the existing Python package and native SchedulerCAPI surface.

The migration architecture is:

1. Retain Greenlet as the stackful continuation backend during compatibility migration.
2. Create a separate Bevy-free Rust workspace crate inside the Bevy Defer tree for scheduler, tasklet, channel, run-control, callback, metric, and lifecycle policy.
3. Keep the current C++ Python types, parser functions, Greenlet calls, GC hooks, and SchedulerCAPI population as the first compatibility facade.
4. Move one decision family at a time behind a narrow, panic-contained FFI boundary.
5. Keep Carbon runnable order in a dedicated deterministic queue. Do not use async-executor scheduling order as the Carbon oracle.
6. Use the local async-executor fork only after a path dependency or patch actually selects it and Cargo metadata proves that selection.
7. Preserve defined legacy behavior exactly unless a defect is fixed in both implementations or a divergence is explicitly approved.
8. Keep Bevy integration optional. A Bevy worker may wake an owning Python thread, but may never switch a Greenlet owned by another thread.
9. Retain the legacy backend through an observation and rollback window.

The central correction from v1 is contractual:

- **Legacy descriptive behavior** records what Carbon actually does, including awkward reachable states.
- **Target safety invariants** record what a cleaner Rust design should guarantee.
- **Approved divergences** record deliberate differences and their separate expected traces.

These three contracts must never be merged into one property suite or one state enum. The final differential rule is **zero unexplained or unclassified mismatches**, not zero differences of every kind.

## 2. Planning boundaries

### 2.1 In scope

- ScheduleManager, Tasklet, Channel, their Python wrappers, QueueChannel interactions, and native SchedulerCAPI behavior.
- Exact scheduler order, continuation transfer, channel rendezvous, callbacks, counters, ownership, GC, teardown, and thread affinity.
- A deterministic Rust compatibility kernel under the Bevy Defer source tree.
- CMake and Cargo integration for a Rust static library consumed by the existing extension.
- Characterization, differential, property, ABI, ownership, sanitizer, concurrency, teardown, and performance evidence.
- A separately feature-gated Bevy host adapter.
- An explicit defect and divergence decision process.

### 2.2 Out of scope

- No source, test, manifest, or roadmap-v1 edit is authorized merely by this document.
- No conversion of synchronous Python tasklet bodies into Python or Rust async functions.
- No removal of Greenlet without a separate continuation-equivalence proposal.
- No public Python API cleanup or SchedulerCAPI field change.
- No new C-compatible public header. The existing capsule is conventionally called a C API, but its public header and repository consumers are C++.
- No free-threaded Python guarantee in this migration.
- No promise of subinterpreter isolation beyond characterized legacy behavior.
- No mandatory Bevy App, World, ECS schedule, frame clock, or async-executor pump in standalone Python mode.
- No silent repair of legacy defects only in Rust.
- No automatic adoption of a clean state machine, transactional channel algorithm, scoped run budgets, mutexes, command queues, or bounded teardown as if they were baseline facts.

### 2.3 Requirements language

- **MUST** is an acceptance requirement.
- **MUST NOT** is a prohibited migration behavior.
- **SHOULD** is the preferred design unless contrary evidence is recorded.
- **MAY** is optional and cannot weaken a MUST.
- A phase is not complete because code exists. It is complete only when its current evidence satisfies its exit gate.

## 3. Contract taxonomy and compatibility authority

### 3.1 Contract classes

Every behavior row, test, trace, and differential mismatch MUST have exactly one class.

| Class | Meaning | Oracle | Acceptance |
|---|---|---|---|
| Baseline parity | Reproducible, defined legacy behavior to preserve | Audited runtime trace plus trusted tests or public contract | Exact match |
| Baseline defect, decision pending | Suspicious behavior whose disposition is not approved | Legacy trace, source order, ownership evidence, and sanitizer result | Blocks implementation of that row |
| Fix-both defect | A defined correction applied to legacy and Rust before comparison | New regression on a re-pinned baseline | Exact match to corrected baseline |
| Approved divergence | Deliberate Rust behavior different from legacy | One expected legacy trace and one expected target trace | Each backend matches its own named trace |
| Undefined or unstable legacy behavior | C/C++ undefined behavior or nonportable memory corruption | Source and sanitizer evidence, not a portable output | Replace only through an approved defined result |
| Opt-in host extension | New Bevy or non-GIL functionality outside standalone parity | Extension contract plus standalone-off trace | No standalone effect; extension invariants pass |
| Unsupported boundary | Deliberately rejected environment or operation | Explicit error/rejection contract | No partial mutation or accidental execution |

No harness may normalize an approved divergence away. Reports MUST show the divergence class, decision identifier, legacy expectation, target expectation, and approval.

### 3.2 Evidence authority is row-specific

V1's blanket rule that existing tests are authority number one is removed.

Use the following process:

1. An explicit approved compatibility or divergence decision governs the affected row.
2. Reproducible behavior of the pinned baseline governs defined runtime semantics.
3. An audited test is authoritative only for the assertion it actually executes.
4. The frozen public Python surface, native header, precompiled consumers, and documented ownership conventions govern their respective API or ABI dimensions.
5. User documentation is supporting evidence.
6. Comments are explanatory evidence only. Executed implementation order outranks a stale comment.

For undefined behavior, dangling pointers, or memory corruption, do not freeze a random runtime result. Use source and sanitizer evidence to approve a defined correction.

### 3.3 Test trust classes

Every historical Python and native test MUST be classified before it is used as an oracle.

| Class | Meaning | Permitted use |
|---|---|---|
| Trusted | Assertion, thread propagation, cleanup, and ownership are audited | Direct oracle |
| Informative | Exercises useful behavior but has incomplete postconditions | Scenario seed only |
| Suspect | Ordering, ownership, cleanup, or exception capture may be wrong | Requires a reliable parallel probe |
| Broken | Does not assert what its author intended | Historical regression only; never authority |
| Sanitizer-only | Valid only in an isolated debug or sanitizer process | Defect evidence |
| ABI-only | Establishes layout/import/calling behavior, not scheduler semantics | ABI gate only |

The forms such as self.assertRaises(RuntimeError, t.switch()) inside worker functions are broken because the call is evaluated before assertRaises and the worker exception is not automatically rethrown by join. The existing tests remain historical inputs, but a synchronized worker-result probe MUST establish the intended contract.

Native tests that give a new PyObject_GetAttrString reference to PyTuple_SetItem and later decref both the tuple and the original pointer cannot be ownership authorities. A parallel audited probe MUST use a new, borrowed, and stolen-reference ledger and run under debug CPython and ASan or LSan where supported.

### 3.4 Decision records

Every fix-both defect or approved divergence MUST have a decision record containing:

- stable decision ID;
- affected public operations and contract rows;
- baseline commit and reproducible trace;
- safety, compatibility, ABI, and ownership impact;
- chosen disposition and rejected alternatives;
- legacy expected trace;
- target expected trace;
- tests written before implementation;
- rollback behavior;
- release-note requirement; and
- named approving authority.

An unapproved recommendation is not an approved divergence.

## 4. Corrected legacy tasklet and queue model

### 4.1 Do not use one mutually exclusive parity enum

Carbon exposes orthogonal state dimensions. The compatibility model MUST preserve them separately.

| Axis | Required fields |
|---|---|
| Identity | tasklet ID, manager ID, owner Python thread-state identity, is_main |
| Binding | callable_bound, bound arguments state |
| Continuation | Greenlet present, alive, parent continuation |
| Execution | is_current, paused |
| Runnable representation | scheduled flag, intrusive previous/next IDs, queue-owned reference |
| Channel representation | blocked flag, direction, channel ID, blocked previous/next IDs, waiter-owned reference |
| Transfer | transfer_in_progress, value/exception/throw packet |
| Control | reschedule request, tagged removal, pending kill/throw |
| Metadata | times_switched_to, timestamps, handler/context policy |
| Lifetime | wrapper clearing/deallocating, manager closing, strong and non-owning edges |

Rust SHOULD encode each axis with a narrow type rather than unrelated unchecked booleans. It MUST NOT derive alive, paused, scheduled, blocked, or current from one parity enum.

### 4.2 Reachable legacy configurations

At minimum, Phase 1 MUST reproduce these configurations without normalization.

| Configuration | Callable | Greenlet | Alive | Paused | Runnable linked or scheduled | Channel wait |
|---|---:|---:|---:|---:|---:|---:|
| Fresh, no callable | No | No | No | No | No | No |
| BoundDormant | Yes | No | No | No | No | No |
| BoundPaused | Consumed into Greenlet | Yes | Yes | Yes | No | No |
| Ready | Consumed into Greenlet | Yes | Yes | Usually no | Yes | No |
| ActiveLinked | Consumed into Greenlet | Yes | Yes | No | Yes until SwitchTo returns | No |
| Blocked ordinary tasklet | Consumed into Greenlet | Yes | Yes | Path-dependent | No after committed block | One FIFO |
| Main blocked on channel | Main continuation | Yes | Yes | Path-dependent | Manager sentinel relationship plus wait membership | One FIFO |
| Trapped paused run | Consumed into Greenlet | Yes | Yes | Yes | Yes | No |
| Dead | Historical metadata only | Dead or cleared | No | Path-dependent public view | No | No |

The target may later define cleaner internal states, but each legacy snapshot MUST map to one of:

- exact target representation;
- explicit temporary compatibility representation;
- approved divergence; or
- target-only invalid state that is never used as a baseline assertion.

### 4.3 Correct lifecycle transitions

| Operation | Legacy source | Legacy effect |
|---|---|---|
| construct without callable | Fresh | No callable, no continuation, not alive, not runnable |
| construct or bind callable only | Fresh or rebindable state | BoundDormant; callable stored, no Greenlet, not alive, not runnable |
| bind with args or kwargs | Bound or rebindable state | Greenlet initialized, alive, paused, not runnable |
| setup or tasklet call | Valid bound or rebindable state | Greenlet initialized, alive, inserted runnable |
| insert | Detached valid tasklet | Inserted at back and ordinary paused view updated |
| remove | Runnable | Detached and paused while alive |
| run on alive paused tasklet | Paused | Insert first, then route through manager Run |
| trapped run on paused tasklet | Paused | Insert remains; switch aborts; paused plus scheduled is observable |
| normal completion | ActiveLinked | Removal and possible reschedule handling occur after control returns |

Bind and Setup MUST have separate parser, transition, and trace rows.

### 4.4 Active tasklets remain runnable-linked

ScheduleManager selects a tasklet while it is still linked in the intrusive runnable chain, calls SwitchTo, and removes or reinserts it only after control returns.

Therefore:

- current and runnable-linked are not mutually exclusive;
- scheduled and current are not mutually exclusive;
- next and prev during Python execution are compatibility observations;
- queue ownership cannot be released before the switch merely to obtain a clean Running state; and
- dequeue-before-run is an approved divergence unless every affected observation is proven equivalent.

The initial Rust parity scheduler SHOULD reproduce ActiveLinked directly. A later cleanup may be proposed only through the divergence process.

### 4.5 Correct tasklet.switch contract

tasklet.switch is not a raw isolated Greenlet switch.

The parity algorithm is:

1. validate target liveness, ownership, blocked/current/main rules, and pending errors;
2. if a detached live target is allowed, insert it into its manager queue;
3. route the selected target through ScheduleManager::Run(target);
4. establish the same parent and run boundary used by the baseline;
5. attempt the continuation transfer;
6. after return, follow the baseline parent and Yield path; and
7. perform queue removal, reinsertion, callbacks, counters, and errors at their actual points.

Traces MUST distinguish switch, run, and ordinary scheduler.run, but MUST NOT claim switch bypasses the manager.

### 4.6 Main may block on channels

Main may enter either channel wait FIFO. ScheduleManager::Yield then runs other runnable tasklets until main is matched and removed, or until deadlock/error rollback occurs.

The descriptive property is:

- main may temporarily occupy exactly one channel direction queue;
- other tasklets may progress while main waits;
- a successful match removes main exactly once;
- a deadlock or trapped/error rollback restores the documented public channel state and ownership; and
- main's manager-sentinel relationship does not prohibit channel membership.

The false invariant that main is never in a channel wait queue is prohibited.

### 4.7 Trap points are operation-specific

Do not state that switch_trap or block_trap universally runs before mutation.

| Path | Actual legacy point |
|---|---|
| Direct Tasklet::SwitchTo | switch_trap returns before times_switched_to, SetCurrentTasklet, timeout switch accounting, callbacks, and Greenlet switch |
| run on paused tasklet | target is inserted before SwitchTo reaches switch_trap |
| receive without counterpart | tasklet reference, receive FIFO, direction, and balance mutate before block_trap, then roll back |
| send without counterpart | channel callback and transfer_in_progress mutation occur before block_trap and closed validation |
| matched channel plus preference scheduling | counterpart transfer and owner-queue state may mutate before a later scheduling attempt reaches switch_trap |

Target preflight or transactional behavior is allowed only when classified as exact parity after proof or as an approved divergence.

### 4.8 Nested and flat traversal remain separate contracts

Nested scheduling remains the default compatibility mode.

In nested mode:

- a tasklet.run establishes the baseline parent and an entry boundary associated with the queue tail present at entry;
- work appended beyond the bounded region may remain for a later run;
- scheduler.run from main has different reach and may continue through newly appended work;
- main-blocked channel progress follows its dedicated run-until-unblocked objective; and
- limited-run checks occur at the baseline scheduling boundaries, not at arbitrary Future polls.

Flat mode remains an explicit supported global mode. It changes immediate target placement and queue restoration, including FRONT_PLUS_ONE behavior, without authorizing removal of nested mode or a default change.

The oracle MUST characterize both modes with tasklets created before and during a run. A generic drain-until-empty loop cannot represent all cases.

## 5. Corrected run budgets and timeout metrics

### 5.1 Separate traversal boundaries from budget storage

Nested tasklet traversal boundaries are real scheduler semantics. Limited-run budget storage is a separate concern.

The baseline keeps run type, task limit, deadline, and related values as ambient mutable manager fields. A nested limited run can overwrite them and then reset the manager to STANDARD, corrupting an outer limited run.

V2 does not silently repair this behavior with a RunScope stack.

The initial parity implementation MUST:

- represent nested traversal boundaries accurately;
- preserve ambient legacy budget behavior after characterization; and
- keep a clean restoring budget stack behind an unapproved target proposal until a divergence decision exists.

If scoped restoration is approved, the differential oracle MUST expect the legacy corruption trace on the legacy side and the restored outer budget on the target side.

### 5.2 Timeout counter semantics

The public timeout counters are process-global compatibility state, not per-manager state.

| Counter | Baseline scope | Increment meaning |
|---|---|---|
| tasklets switched last timeout run | Global last timed run | OnSwitch current-tasklet transitions while the timed-run mode is active |
| tasklets completed last timeout run | Global last timed run | Successful runnable removal or dequeue cycles in the timed-run cleanup path |

Consequences:

- A switch rejected by the early switch_trap check does not increment the switched counter.
- The stale comment claiming an attempted trapped switch increments it is not authoritative.
- The completed counter may count repeated scheduling cycles of one still-alive yielding tasklet.
- A timed run resets the global published values.
- A later timed run in another Python thread may replace what the getters return.

Internally, Rust SHOULD name the second quantity dequeue_cycles until yielding-tasklet characterization proves a narrower meaning. The public function name and ABI field remain unchanged.

### 5.3 Required limited-run characterization

Before implementation, record:

- zero, negative where accepted, expired, and tiny deadlines;
- first-progress behavior at zero timeout;
- a first selected tasklet rejected by switch_trap;
- one tasklet that repeatedly calls schedule;
- nested count-limited inside timed and timed inside count-limited runs;
- callback reentrancy that invokes a limited run;
- error exits;
- main blocked on a channel during a limit; and
- two Python threads coordinated so global reset and last-writer visibility are observable.

No per-manager publication is allowed without an approved compatibility break.

## 6. Corrected channel contract

### 6.1 Rendezvous and wait queues

Carbon Channel remains a synchronous FIFO rendezvous channel with independent sender and receiver wait lists.

- Positive balance counts waiting senders.
- Negative balance counts waiting receivers.
- A match selects one counterpart in FIFO order.
- Preference changes continuation order, not counterpart selection.
- Values, exception forms, and throw triples retain their distinct ownership and restore rules.

Main is not excluded from either wait list.

### 6.2 Preference has two entrypoint contracts

The Python property and native SchedulerCAPI setter MUST not share one clamping parser.

| Entrypoint | Ordinary input below -1 or above 1 |
|---|---|
| Python channel.preference setter | Succeeds and leaves the previous preference unchanged |
| Native PyChannel_SetPreference | Clamps to -1 or 1 |

Python -1, 0, and 1 set the corresponding value. PyLong_AsLong overflow is a separate defect case because the current path can leave an exception pending while using -1. It MUST be characterized and given a decision before implementation.

### 6.3 Legacy receive order

For an unmatched receive, the baseline order is:

1. channel callback runs using counterpart absence at entry;
2. current tasklet obtains the waiter reference;
3. current is inserted into the receive FIFO;
4. blocked direction and balance change;
5. block_trap is checked;
6. a trapped path unlinks and releases the waiter reference; or
7. closed/closing validation follows and takes its own rollback path;
8. if blocking remains valid, control yields.

The closed rollback appears not to release the same waiter reference used by the trap rollback. That branch is a named defect, not a generic ownership concern.

A Rust receive may validate before insertion only after trace-on/off, callback, refcount, finalizer, and public-state evidence proves exact parity, or after an approved divergence.

### 6.4 Legacy send order

For a send attempt, the baseline order includes:

1. channel callback using receiver absence at entry;
2. transfer_in_progress set on the current tasklet;
3. current/main, block_trap, and closed/closing validation on the unmatched path;
4. waiter insertion or counterpart match;
5. transfer delivery and owner-manager scheduling;
6. preference-dependent scheduling attempt; and
7. completion or error.

Some early errors do not restore transfer_in_progress. Because this flag affects tasklet death after a caught error, validate-then-mutate is not presumed equivalent. Trapped-send and closed-send probes MUST let the tasklet catch the error, return, and expose liveness, paused, scheduled, transfer, and refcount results.

### 6.5 channel_callback will_block meaning

The historical will_block argument means **counterpart absent at callback entry**.

It is computed:

- before block_trap;
- before closed validation;
- before the callback can reenter and alter queues; and
- for operations that may later fail.

The internal trace field SHOULD be named counterpart_absent_at_callback_entry. The public callback argument name remains unchanged.

### 6.6 Compatibility synchronization

Standalone Python compatibility mode MUST keep canonical channel and manager mutation serialized by the GIL. Native SchedulerCAPI wrappers acquire the GIL before entering current channel logic.

An independent channel mutex is not a baseline requirement. It is an opt-in host-extension design with new lock ordering and reentrancy semantics.

If a later extension permits non-GIL channel mutation:

- define one total lock order;
- hold no lock across Python code, a Python callback, a decref that may finalize user code, or a Greenlet switch;
- prove standalone traces are unchanged when the extension is disabled;
- reject recursive acquisition;
- use barrier-driven deadlock and reentrancy tests; and
- classify the extension separately from Python 3.12 parity.

### 6.7 Cross-thread scheduling commitment

The compatibility linearization point is the synchronous owner-manager queue mutation performed during rendezvous while the operation holds the GIL.

The required sequence is:

1. select and unlink the counterpart;
2. attach the transfer;
3. synchronously commit released-tasklet scheduling into its owner manager;
4. make scheduled, links, run count, and callback-visible state reflect that commit;
5. optionally enqueue a wake notification; and
6. return or continue preference scheduling.

A host command queue MAY carry a wake notification for already-committed work. It MUST NOT defer the logical scheduling mutation unless every intervening read has an explicitly approved pending-command model.

### 6.8 QueueChannel remains a Python compatibility wrapper

QueueChannel is buffered Python behavior layered over the rendezvous channel. It stores value or exception records in a Python deque and calls the base channel only when a receiver is already waiting or closing behavior requires it.

The migration MUST preserve:

- nonblocking buffered sends;
- receive and iterator order;
- send_exception and send_throw record behavior;
- send_sequence;
- length and balance conventions;
- main-tasklet blocking when the buffer is empty; and
- interaction with close, closing, and block_trap.

The current wrapper creates a fresh threading.Lock inside individual operations. That does not provide shared mutual exclusion and MUST NOT be elevated into a Rust locking requirement without a characterization that proves an observable dependency.

## 7. Callback timing, failure, and ownership

### 7.1 Schedule transition protocol

The baseline transition MUST be represented as separate ordered points:

1. target selected;
2. target times_switched_to incremented;
3. timeout switched counter incremented by OnSwitch when timed mode is active;
4. Python schedule callback entered with previous and next;
5. Python callback returned or left an exception pending;
6. fast native schedule callback attempted even if the Python callback left an exception;
7. current pointer committed to next;
8. Greenlet switch attempted;
9. switch returned or failed;
10. queue removal or reinsertion performed;
11. timeout dequeue-cycle counter incremented where the legacy cleanup does so; and
12. parent/current return transition performed.

During callback entry:

- scheduler.getcurrent returns previous; and
- next.times_switched_to already includes the new switch.

Committing current before the callback is incompatible even if the callback receives the correct argument pair.

### 7.2 Callback exception behavior

The legacy Python callback return value is ignored. A callback may leave a Python exception pending, and the fast callback is still attempted.

Every callback trace MUST record:

- entry and exit;
- pending-exception state;
- fast callback attempt and outcome;
- current before and after;
- whether Greenlet switching was attempted;
- queue or channel mutations;
- final public return or exception; and
- cleanup and reference effects.

Callback failure is part of Phase 1 characterization and every later transition phase. It is not deferred to callback-storage migration.

### 7.3 Setter ownership is entrypoint-specific

The ownership ledger MUST distinguish:

| Path | Current preparation before storage |
|---|---|
| Python schedule/channel setter | INCREF new callable, then give storage an owned pointer |
| Native SchedulerCAPI setter | Pass incoming pointer without the same INCREF |
| Shared storage | DECREF old slot, then store incoming pointer |

The native ownership expectation is internally inconsistent with tests that continue to own and decref their pointer. Existing consumers MUST be audited before choosing borrowed-plus-INCREF or transferred-reference semantics.

### 7.4 Previous-callback return defect

The Python setters currently save a raw old pointer, replace the slot, allow storage to DECREF it, and return the saved pointer without a compensating INCREF. If the slot held the final strong reference, this can return a dangling PyObject.

The recommended disposition is fix-both, not random-output parity:

1. reproduce in an isolated debug/sanitizer process;
2. add a regression that removes all external strong references;
3. approve safe returned-reference semantics;
4. correct the legacy setter;
5. re-pin the baseline; and
6. require Rust to match the corrected behavior.

### 7.5 Required mixed-state bridge

Moving scheduler or channel decisions before moving callback and metric storage requires an explicit bridge.

| Rust-owned decisions | Temporary legacy bridge until storage migration |
|---|---|
| current transition | Invoke legacy Python and fast schedule callback slots at the exact protocol points |
| timed run | Publish to the legacy-compatible global timeout counters |
| channel attempt | Invoke the legacy global channel callback before validation with historical will_block meaning |
| manager/tasklet/channel lifecycle | Continue updating legacy-compatible global active/all-time counts |

Phase 8 may change where storage lives. It may not introduce behavior that Phase 5 or Phase 6 already promised.

## 8. Thread affinity and Bevy host rules

### 8.1 Greenlet owner-thread invariant

Every Greenlet create, parent operation, switch, throw, and destruction-sensitive call MUST occur:

- with the GIL held;
- on the exact owning Python thread;
- under the owning Python thread-state and ScheduleManager identity; and
- outside any Rust mutex guard.

Operating-system thread equality alone is insufficient if the wrong Python thread state or manager is active.

### 8.2 Bevy pump rule

A Bevy system may pump a Carbon manager only if the executing thread is the manager's exact Python/Greenlet owner and the current thread-state lookup resolves to that manager.

Any other Bevy worker may only:

- submit auxiliary data that does not mutate Carbon order;
- enqueue or coalesce a wake request; and
- notify the owner thread.

It may not call Greenlet, make a tasklet current, drain an arbitrary manager, or reinterpret a selected manager as thread-safe.

### 8.3 Host wake semantics

A wake is notification, not scheduling commitment. The runnable mutation is already visible before the wake. Wake coalescing is allowed only if it does not lose the fact that committed work exists.

Wrong-thread pump attempts MUST fail deterministically before any continuation or current-tasklet mutation.

## 9. Target repository and crate architecture

### 9.1 Selected Bevy-free boundary

V2 chooses a separate workspace crate, not a module-only import rule.

Recommended layout:

- **bevy_defer/carbon_core/**
  - safe Rust scheduler, tasklet state axes, channel selection, run control, packets, metrics model, identities, and lifecycle policy;
  - no Bevy dependency;
  - no CPython or Greenlet call;
- **bevy_defer/carbon_ffi/**
  - static library and narrow C ABI;
  - CPython/Greenlet pointer bridge, panic containment, traversal/clear callbacks, and error translation;
  - depends on carbon_core, not on the root bevy_defer package;
- **bevy_defer/src/carbon_bevy/** or a sibling optional adapter crate
  - Bevy plugin/resource/system integration;
  - depends on carbon_core;
  - never required by standalone Python;
- **bevy_defer/**
  - existing Bevy Defer package and features;
  - may expose the optional adapter;
- **bevy_defer/async-executor/**
  - local auxiliary Future executor fork;
  - not the canonical Carbon queue.

The root bevy_defer package currently depends on Bevy unconditionally. Therefore the standalone extension MUST link carbon_ffi or carbon_core directly, not the root package.

### 9.2 Exact async-executor source selection

Workspace membership and dependency selection are separate operations.

When code is authorized, use both:

1. add async-executor to workspace.members so its tests and package commands participate; and
2. change the root dependency to an explicit local source, preferably:

   async-executor = { version = "1.14.0", path = "./async-executor" }

An exact root patch for crates.io is an alternative only if Cargo metadata proves it wins resolution.

Required evidence:

- cargo metadata identifies the async-executor manifest under the repository;
- the bevy_defer resolve node points to that package ID;
- cargo tree shows no registry async-executor selected for Bevy Defer;
- the lockfile records the intended source; and
- a deliberate local test mutation or package fingerprint proves the built code is local without leaving that mutation committed.

Adding only workspace membership fails this gate.

### 9.3 Bevy-free graph proof

The carbon_core package gate is:

- cargo metadata shows a distinct package;
- cargo tree for carbon_core contains no bevy package;
- carbon_core builds and tests with no Bevy feature;
- its public and private source contains no bevy import; and
- carbon_ffi can link it in a standalone extension build without the root bevy_defer crate.

An import lint alone is not sufficient.

| C++ Python/native facade | Existing types, parsing, docstrings, capsule, GIL entry, initial GC hooks | Scheduler policy |

### 9.5 Deterministic queue requirements

The queue API needs semantic operations:

- enqueue_back;
- enqueue_run_next;
- enqueue_front_plus_one;
- remove_linked;
- select_after_base;
- preserve ActiveLinked during continuation execution;
- apply tagged removal;
- apply reschedule front or back request;
- recompute run count; and
- expose stable previous/next identities for compatibility snapshots.

Duplicate insertion behavior MUST be classified before cleanup. InsertTaskletToRunNext currently acquires a reference before discovering an already-scheduled tasklet. Its public reachability requires a reentrancy and call-site probe.

### 9.6 async-executor role

Do not use async-executor run, Runner, random selection, local stealing, waker order, Task cancellation, or detach semantics as the Carbon scheduler.

It MAY provide:

- auxiliary I/O and timers;
- non-Carbon Future work;
- a host wake signal; or
- an independently tested completion primitive.

Any modification to async-executor requires its own focused tests and must not alter upstream behavior for ordinary users.

### 10.5 GC traversal and clear protocol

Keeping the C++ wrapper is insufficient once Rust owns Python references.

Every GC-tracked wrapper whose Rust handle owns Python objects MUST call panic-contained FFI operations equivalent to:

- carbon_tasklet_traverse(handle, visitproc, arg): under the GIL, visit every direct strong Python edge exactly once without mutation, allocation, INCREF/DECREF, or user code;
- carbon_tasklet_clear(handle): under the GIL, detach and release all cycle-forming Rust-owned edges, remain idempotent, and leave a deallocation-safe tombstone.

Equivalent operations are required for Channel or Manager wrappers if they gain cycle-forming Rust-owned edges.

Tests MUST construct cycles through callable, args, kwargs, handler, context getter, transfer packets, exception state, Greenlet/frame relationships, and parent/manager relationships. They MUST prove collection, weakref behavior, finalizer order, repeated tp_clear safety, and no hidden Rust edge.

### 10.6 FFI safety rules

- No Rust panic crosses C or Python.
- No Python C API call occurs without the GIL.
- No Python reference release occurs on an arbitrary worker thread.
- No Greenlet operation occurs on the wrong owner thread.
- No Rust lock is held across Python, callback, finalizer-capable DECREF, or Greenlet execution.
- Raw handles validate kind, generation, liveness, wrapper clearing, manager closing, and owner where applicable.
- Error returns set the intended Python exception.
- Success returns do not accidentally leave an exception pending unless that pending-exception behavior is a classified legacy row.
- Unsafe code is concentrated in CPython, Greenlet, callback, and handle boundaries.

## 12. Behavioral oracle and trace design

### 12.1 Separate property suites

Use at least three named suites.

| Suite | Subject | Legacy expectation |
|---|---|---|
| legacy_descriptive_properties | Defined reachable Carbon behavior and ordering | Must pass, except isolated undefined cases are excluded by named decision |
| target_safety_properties | Chosen Rust invariants such as handle generations and approved transactional rules | May fail on legacy only where a decision maps the difference |
| differential_contract_properties | Backend-specific expected traces for parity and divergences | Each side matches its classified expectation |

Do not run target safety properties against legacy and call valid legacy states failures. Do not weaken target safety properties so legacy can pass.

### 12.2 Lossless snapshots

A trace snapshot SHOULD contain:

- manager, tasklet, channel, run-boundary, and packet IDs;
- is_main and is_current;
- callable_bound and continuation_present;
- alive, paused, scheduled, blocked, and transfer_in_progress;
- runnable previous and next IDs;
- channel ID, direction, blocked previous and next IDs;
- parent ID;
- reschedule, tagged-removal, and pending-control values;
- times_switched_to;
- callback and pending-exception state;
- run type, budget, deadline class, and global timeout counters;
- channel preference, balance, close state, and both FIFO orders; and
- debug-only ownership deltas recorded without extending Python lifetimes.

### 12.3 Trace event protocol

Scheduler events MUST distinguish:

- selected;
- times_switched_to increment;
- timed OnSwitch increment;
- Python callback enter/exit;
- fast callback enter/exit;
- current commit;
- Greenlet attempt/return/failure;
- queue remove/reinsert;
- dequeue-cycle increment; and
- parent/current return.

Channel events MUST distinguish:

- entry queue snapshot;
- counterpart-absence decision;
- callback enter/exit;
- transfer flag mutation;
- trap and closed checks;
- waiter insertion/removal and balance;
- match/pop/unblock;
- synchronous owner-manager commit;
- optional wake; and
- preference schedule attempt.

### 12.4 Non-observer-effect invariants

Trace instrumentation MUST:

- use numeric IDs or non-owning pointer-plus-generation sidecars;
- retain no persistent strong Python reference;
- never call repr, str, equality, hashing, descriptors, properties, weakref callbacks, or arbitrary Python code;
- read primitive native or Rust fields only;
- not keep a PyObject alive beyond the lifetime already guaranteed at the event point;
- avoid file I/O and Python serialization in the transition hot path;
- use a preallocated or otherwise bounded nonblocking sink;
- order events by sequence number rather than a wall-clock read;
- not add a new runtime lock order;
- tolerate partially destroyed objects through explicit tombstones; and
- be completely disabled without changing ordinary behavior.

Each scenario MUST run with tracing off and on. Deterministic non-trace observations must match exactly. Timed boundary scenarios must use guard bands, record instrumentation overhead separately, and match the approved timing outcome class rather than hide an altered result.

### 12.5 Differential normalization

Normalize only:

- raw addresses mapped to stable identities;
- absolute timestamps while retaining order and approved duration tolerances;
- platform thread numbers while retaining equality relationships; and
- explicitly unspecified representation text.

Never normalize:

- order;
- queue or FIFO membership;
- scheduled, paused, blocked, alive, or current combinations;
- exception type, message, args, pending state, cause/context, or traceback relationships;
- callback timing;
- counter scope or values;
- reference/finalizer outcome;
- cross-thread visibility; or
- an approved divergence.

2. Require exact owner-thread/manager identity before pumping.
3. make foreign workers wake-only;
4. define ordering relative to existing Bevy Defer executor, timers, watchers, and commands;
5. leave explicit scheduler.run available;
6. keep auxiliary Futures outside Carbon order; and
7. define shutdown as stop pump, reject new extension requests, drain auxiliary work, then close managers.

Exit:

- standalone no-Bevy traces are unchanged;
- wrong-thread pump attempts perform no continuation mutation;
- headless owner-thread integration is deterministic;
- existing Bevy Defer tests remain green; and
- C21 passes.

Rollback: disable the adapter feature.

### Phase 11: Controlled switchover

Actions:

1. Run CI in legacy, Rust, and differential modes.
2. Make Rust opt-in first.
3. Collect crash, deadlock, queue, blocked-channel, callback, global-counter, GC, and teardown evidence.
4. Promote only after every platform and classified contract gate passes.
5. Keep an early startup rollback selector.
6. Prohibit backend switching after any manager/tasklet/channel exists.
7. Retain the legacy backend for an agreed observation window.
8. Remove legacy scheduling logic only through separate approval.

Exit:

- zero unexplained or unclassified mismatches;
- all approved divergences remain visible in reports and release notes;
- no regression beyond approved performance and safety budgets;
- operational rollback is demonstrated; and
- production evidence covers representative workloads.

### Phase 12: Optional post-parity safety divergences

Clean run-scope restoration, validate-before-mutate channels, new mutex-based host APIs, per-manager metrics, and other semantic improvements belong here unless fixed in both implementations earlier.

Each item needs its own decision, tests, release note, compatibility-mode policy, and rollback. Phase 12 is not a reason to weaken Phase 0 through Phase 11 parity.

### 15.1 Corrected descriptive properties

- Exactly one current identity exists per live manager, but the current tasklet may remain runnable-linked.
- Main belongs to its manager and may temporarily join one channel FIFO.
- BoundDormant and BoundPaused are valid.
- Paused plus scheduled is valid in the trapped paused-run path.
- Runnable and channel link reciprocity hold at classified stable observation points.
- Channel balance equals sender count minus receiver count using Carbon's sign convention.
- A successful rendezvous transfers one packet.
- A direct switch_trap rejection does not increment timeout switched count.
- Global timeout getters expose the last timed-run publication.
- Schedule callback sees previous as current and next with incremented times_switched_to.
- Channel callback will_block reflects counterpart absence at callback entry.
- Cross-thread match commits to the owner manager before wake/pump.
- Greenlet execution never occurs on a foreign owner thread.

### 15.2 Target-only safety properties

These are not baseline claims unless separately proven:

- stale generational handles fail closed;
- Rust panic never crosses FFI;
- each Rust-owned Python edge is traversed and cleared exactly once;
- no lock crosses Python or Greenlet execution;
- approved validate-before-mutate paths leave no partial state;
- approved scoped budgets restore outer state;
- approved teardown terminates within its deterministic bound; and
- optional host extensions have no effect when disabled.

## 16. Performance plan

Correctness and classified compatibility precede optimization.

Measure:

- queue insertion, removal, run-next, and front-plus-one distributions;
- Greenlet switch and return;
- short and long scheduler.run workloads;
- timeout overshoot and trace overhead;
- same-thread and cross-thread rendezvous;
- callbacks enabled, disabled, reentrant, and raising;
- memory per manager/tasklet/channel/waiter;
- allocations per yield and rendezvous;
- GC and thread-exit cleanup;
- wake coalescing; and
- optional Bevy frame-pump cost.

Compare equivalent builds and workloads. Record variance and p50/p95/p99, not only a mean.

Do not improve results by:

- dequeuing before execution when it changes compatibility;
- reordering callbacks;
- batching visible transitions;
- replacing FIFO with work stealing;
- deferring Python releases to a worker;
- suppressing difficult states;
- changing timeout counter meaning; or
- disabling invariant checks in only one compared build.

Performance budgets MUST be derived from measured baseline data and approved before switchover. V1's provisional percentages are not contractual evidence.

## 20. Definition of done

The migration is complete only when:

- carbon_core and carbon_ffi are authoritative for the migrated behavior and remain Bevy-free;
- Greenlet is behind the owner-thread continuation interface;
- local async-executor selection is proven;
- every public behavior row has a contract class and current evidence;
- trusted historical tests and reliable replacement probes pass;
- historical suites still run and their limitations remain visible;
- legacy descriptive, target safety, and differential property suites pass independently;
- every approved divergence matches both named backend expectations;
- callback order, reentrancy, failure, and ownership are proven;
- global timeout metrics and cross-thread visibility match the compatibility contract;
- channels preserve FIFO, preference, balance, main blocking, synchronous owner commitment, and cleanup;
- all Rust-owned Python edges participate in CPython GC;
- no panic, wrong-thread Greenlet call, stale handle, double release, lost waiter, or unclassified leak remains;

- the opt-in Bevy adapter cannot pump a foreign manager;
- zero unexplained or unclassified differential mismatches remain;
- performance meets measured approved budgets;
- rollback is tested before runtime-object creation;
- divergences are documented for users; and
- legacy logic removal receives separate approval after the observation window.

## 23. Final recommendation

Proceed only after the contract and oracle phases are complete.

The first Rust implementation should reproduce Carbon's real state combinations and transition order, not the cleaner model v1 wished the baseline had. Clean states, transactional channels, scoped budgets, per-manager metrics, mutex-based host APIs, and bounded teardown may be valuable, but they are separate safety decisions.

The modified Bevy Defer tree remains the correct home for the rewrite when the core is a distinct Bevy-free crate, the existing Python/native facade remains stable, Greenlet stays on its owning Python thread, cross-thread scheduling commits synchronously before host wake, and every intentional difference remains explicit and reviewable.
