- Status: planning only; this document does not authorize implementation
- Repository: `QuasarRay/carbon-scheduler-lab`

## 1. Outcome

Build an opt-in Carbon Scheduler compatibility layer on top of the existing
Bevy Defer crate. The layer must let the unchanged Carbon Python package and
native C++ consumers use a Bevy Defer-hosted runtime while preserving the
observable Carbon Scheduler contract: Python API, native capsule ABI,
Greenlet control flow, deterministic tasklet order, channel rendezvous,
callbacks, counters, ownership, and thread affinity.

The experimental implementation remains one additive Cargo package:

`bevy_defer/carbon_compat`

That package will have two mutually exclusive deployment modes:

1. a standalone `_scheduler` extension that owns a private headless Bevy
   host; and
2. an embedded Rust library whose `_scheduler` initializer is registered as
   a CPython built-in module before interpreter initialization.

The two modes use the same compatibility implementation but are never loaded
into one process together. This is the central v5 singleton rule: in embedded
mode, `CarbonCompatPlugin` and `_scheduler` must be the same linked Rust
instance, not two copies compiled from the same Cargo package.

Carbon policy remains deterministic and private to the compatibility layer.
Bevy Defer supplies the real `World`-scoped, owner-thread execution context.
Carbon tasklets are not independent async-executor tasks, and executor wake
order never becomes Carbon runnable order.

## 3. Corrections adopted from the v3 and v4 audits

V5 makes each finding in `report-v3.md` an explicit design decision or phase
gate.

| Audit finding | V5 resolution |
|---|---|
| A Cargo package can appear twice as an `rlib` and a loaded extension | Embedded `_scheduler` is a built-in module registered from the one library linked into the executable; the extension artifact is forbidden in that process |
| Embedded synchronous `scheduler.run()` lacked an initial entry path | Embedded Python capable of calling Carbon begins inside `CarbonDriver`; independent Python cannot pump an application-owned `World` |
| `CoreAsyncPlugin` does not poll executors | The compatibility plugin installs one explicitly configured `run_async_executor` run; `CoreAsyncPlugin` only initializes resources |
| The Greenlet proof omitted the suspended `Future::poll` frame | Phase 1B proves the safety of `Pin<&mut CarbonDriver>`, `Context`, the native switch frame, and cancellation boundaries |
| Driver task ownership and shutdown were vague | The host retains the non-detached `Task<()>`, uses a specified lifecycle, and retires it only after a safe shutdown boundary |
| “The GIL serializes it” was not a Rust sharing model | V5 selects a GIL-gated logical-state cell plus a separate thread-safe wake cell and owner-only non-`Send` host state |
| `useNestedTasklets` was deferred too late | Its process-global flag, getters/setters, and both `Tasklet::Run` branches move in Phase 2 |
| A nested workflow cannot be a repository GitHub Actions workflow | Phase 0 creates an executable scope guard, not a claimed GitHub workflow; root workflow automation requires later authorization |
| CPython/Rust FFI strategy was undecided | V5 selects low-level `pyo3-ffi` plus a narrow C++ Greenlet/capsule shim before behavioral implementation |
| Separate headless and App tests could miss split runtimes | Phase 1B requires one executable that links the plugin, embeds CPython, imports built-in `_scheduler`, and proves shared runtime identity and teardown |

The v4 readiness audit adds five binding corrections:

| v4 audit finding | V5 resolution |
|---|---|
| Plugin attachment occurred after CPython initialization | The bootstrap and plugin attach first; the plugin registers `PyInit__scheduler`; only then may the owner initialize CPython |
| Embedded foreign-manager topology was ambiguous | Standalone supports one manager/headless host per Python thread; experimental embedded supports exactly one Carbon owner and rejects foreign manager creation |
| Live-driver `Drop` left “fail or retain” to implementation | The experiment selects fail-stop `abort` before unwinding or cancellation |
| Cargo pins were descriptive rather than enforceable | `bevy_defer/Cargo.lock` is tracked, Cargo gates use `--locked`, and a checked environment manifest pins non-Cargo inputs |
| Standalone/embedded artifact selection was implicit | Exactly one mode feature is mandatory, build/package commands are frozen, and embedded packaging excludes the extension |

The bootstrap correction also defines the inverse lifecycle: embedded shutdown
reaches driver `Dead` while CPython is usable, CPython finalization runs while
dead App resources still exist, and the App is dropped only afterward.

The audit also confirmed the difficult Carbon-specific parts of v3. V5 keeps
the orthogonal tasklet representation, linked-while-running queue law,
callback ordering, send/receive asymmetry, channel/control coupling,
process-global compatibility state, partial-order treatment of unordered
cleanup, and exact C++ capsule shape.

The local source anchors for the architectural corrections are:

- `bevy_defer/src/lib.rs`: `CoreAsyncPlugin` initializes resources, while
  `AsyncPlugin` installs `run_before_async_executor` and
  `run_async_executor` into configured schedules;
- `bevy_defer/src/executor.rs`: `AsyncExecutor` wraps a crate-private
  `Rc<LocalExecutor>`, `spawn_task` returns a handle, and only
  `run_async_executor(&mut World)` installs the scoped Bevy context and drains
  the executor;
- `bevy_defer/src/spawn.rs`: dropping a returned task handle cancels/drops the
  associated Future;
- `src/ScheduleManager.cpp`, `src/Tasklet.cpp`, and `src/Channel.cpp`: queue,
  switch, callback, channel, and nested-run behavior;
- `src/ScheduleManager.h` and `src/SchedulerModule.cpp`: process-global
  `s_useNestedTasklets` and its Python setters/getters; and
- `include/Scheduler.h`: the C++ capsule table and `PyObject **TaskletExit`.

## 4. Selected runtime architecture

### 4.1 One package, two deployment modes, one instance per process

The package exposes two mandatory, mutually exclusive Cargo mode features:

```toml
[lib]
crate-type = ["rlib", "cdylib"]

[features]
default = []
standalone = []
embedded = []
```

Crate-level guards reject both features together and reject neither feature.
Features select mode-specific code/tests. The crate-type list is static, so
packaging—not feature selection alone—decides which artifact enters a process.

```text
standalone:
  cargo build -p carbon_compat --no-default-features \
      --features standalone --locked
  stage only the platform _scheduler extension and unchanged Python package

embedded:
  cargo build -p carbon_compat --no-default-features \
      --features embedded --locked
  link only the rlib into the executable
  exclude generated _scheduler libraries from module search and packaging

both or neither:
  compile error
```

Every gate records `cargo tree -e features --locked` and fails if feature
unification enables both modes. `--all-features` is intentionally unsupported
for this package because its deployment modes are incompatible.

```text
Standalone Python process
    CPython dlopen(_scheduler extension)
        └── one carbon_compat instance
              └── one headless Bevy host per participating Python thread

Embedded Bevy process
    executable links carbon_compat rlib once
        ├── CarbonCompatPlugin
        └── PyInit__scheduler registered by its bootstrap before Py_Initialize
              └── the same one linked runtime instance
```

The split topology `rlib + dlopen(_scheduler.so)` is forbidden.

Embedded startup has one legal order:

1. on the intended owner OS thread, confirm `Py_IsInitialized() == 0`;
2. construct the Bevy `App`;
3. create one `EmbeddedRuntimeBootstrap` with a fresh generation;
4. add `CarbonCompatPlugin::run_in(...)` using that bootstrap;
5. during plugin build, install owner resources/driver/one runner and call
   `PyImport_AppendInittab("_scheduler", PyInit__scheduler)` exactly once;
6. verify one registered generation/runner after plugin construction;
7. call `Py_Initialize` on that same owner thread;
8. import unchanged `scheduler` and observe `_scheduler` as built-in;
9. compare bootstrap/plugin/module generation identities; and
10. submit the initial Python callable through that exact App driver.

No compatibility plugin, App host, manager, or Greenlet may attach to an
already initialized interpreter in experimental embedded mode. If step 1
fails, bootstrap creation returns an error before compatibility resources
enter the App. Pre-registering the initializer and attaching the plugin later
is not an allowed split bootstrap.

The one-process test verifies built-in origin and generation identity from
bootstrap, plugin, and Python. Equal source or package names are not evidence
of shared state. The embedded fixture also removes the generated extension
from every module search path and fails unless `_scheduler` is built-in.

### 4.2 Standalone host contract

The unchanged Scheduler tests start in ordinary Python and do not own a Bevy
`App`. The loaded extension lazily creates an owner-thread headless host when
that Python thread first needs a manager.

Each headless host:

- owns its minimal `App`/`World` on the Python/Greenlet owner OS thread;
- initializes Bevy Defer core resources;
- owns one `CarbonDriver` Task and one manager;
- invokes public `run_before_async_executor` and `run_async_executor` when
  Carbon needs synchronous progress;
- contains no unrelated Future in deterministic Scheduler tests; and
- never exposes a `World` pointer to Python.

`scheduler.run()` pumps only that thread's owned host until its requested
Carbon boundary completes.

Standalone GIL-enabled CPython supports multiple participating Python threads.
Each thread lazily owns exactly one manager, headless host, driver, and wake
endpoint; none migrates. The process-global logical runtime/channel registry
is shared under the GIL, so a cross-thread rendezvous synchronously commits the
released tasklet into its owner manager before waking that manager's host.

Thread teardown shuts down its host on its creating OS thread. A manager cannot
be rebound between threads or from headless to embedded mode.

### 4.3 Embedded host contract

Experimental embedded mode supports exactly one Carbon-executing Python
thread, one Carbon manager, and one App-owned driver.

The App owns `World`. The module retains no `&mut World`, does not call
`App::update()` from Python, and exposes no generic tick handle. Rust submits a
Python entry callable to the owner-thread driver:

```text
Bevy schedule
    -> run_async_executor(World)
        -> CarbonDriver::poll
            -> submitted Python entry
                -> nested synchronous Carbon calls
```

For the experimental embedded backend:

- module import and inert type inspection may occur before driver entry;
- first manager creation and every mutating/control-transferring operation
  occur on the owner thread inside active driver entry;
- Carbon control/channel operations from any other context raise
  `RuntimeError` before manager creation, queue, counter, callback, transfer,
  wake, or ownership mutation;
- a foreign Python thread cannot create manager B, obtain a current tasklet, or
  participate in a Carbon channel rendezvous;
- a foreign Rust thread may submit only an opaque Bevy-facing host request; it
  cannot read/mutate Carbon state and proves no Carbon cross-thread support;
  and
- independently running Python cannot synchronously drive the App.

Unchanged multi-thread Scheduler tests run in standalone mode. Embedded
multi-manager or embedded-plus-headless-worker support is deferred to a
production topology decision.

### 4.4 Executor installation and ownership

`CoreAsyncPlugin` initializes resources; it does not run executors. The
compatibility plugin owns one configured executor run.

```text
EmbeddedRuntimeBootstrap::new(owner_thread)
CarbonCompatPlugin::run_in(Update).with_bootstrap(bootstrap)
CarbonCompatPlugin::run_in_set(Update, MySet).with_bootstrap(bootstrap)
```

Before CPython initialization, the plugin must:

1. validate the unconsumed bootstrap, owner thread, generation, and
   `Py_IsInitialized() == 0`;
2. register `PyInit__scheduler` exactly once for that generation;
3. install `CoreAsyncPlugin` if absent;
4. add exactly one ordered `run_before_async_executor` then
   `run_async_executor` pair to the chosen schedule/set;
5. install owner resources, retained driver Task, runner marker, and
   generation; and
6. reject a second bootstrap/plugin or configured `AsyncPlugin` in the same
   experimental App.

Failure occurs before interpreter initialization and before manager/Greenlet
creation. An unarmed failed bootstrap may be discarded but never reused.

Manual insertion of another runner is outside the experiment. Ordinary Bevy
Defer Futures share the same executor run and may execute before/after, but
not inside, one synchronous Carbon segment.

Standalone owns a core-only world and calls the public runner functions at a
top-level pump boundary; it never recursively updates its App.

### 4.5 Scheduling-domain boundary

| Bevy Defer owns | Carbon compatibility owns |
|---|---|
| `World` scope and owner-thread executor polling | manager registry and process-global compatibility fields |
| plugin/system placement and wake delivery | deterministic runnable chain and channel FIFOs |
| ordinary Future spawning and polling | tasklet/parent/control/exception policy |
| scoped Bevy access for ordinary Defer Futures | Greenlet calls and Python callback timing |

One long-lived driver Future represents the compatibility work for an owner
host. Individual Carbon tasklets are never spawned into async-executor. A
driver poll executes a complete synchronous Carbon segment with no `.await`
inside scheduler-visible mutations. async-executor decides only when a
requested segment receives an owner-thread poll; it never chooses the next
Carbon tasklet.

### 4.6 Local async-executor policy

The checked-in `bevy_defer/async-executor` fork is not mandatory for the
experiment. First use the dependency selected by the root Bevy Defer
manifest, and record its package ID and source with `cargo metadata --locked` and
`cargo tree --locked`.

Only select or modify the local fork after a focused Phase 1 test proves that
the public `AsyncExecutor::spawn_task` plus `run_async_executor` path lacks a
required capability. If that occurs:

- use an explicit path dependency or `[patch.crates-io]`; workspace
  membership alone does not select dependency source;
- add a regression for the exact missing capability;
- run the fork's unchanged tests and root Bevy Defer tests; and
- continue to keep Carbon ordering out of async-executor.

## 5. CarbonDriver safety and lifecycle

### 5.1 Stable-state shape

`CarbonDriver` must be deliberately small. It owns or references only a
stable heap handle, a manager/runtime generation, and minimal driver state.
Reentrant Python entrypoints cannot obtain an alias to the driver Future
itself.

Scheduler-owned mutable state lives in stable heap allocations reached by
validated generational handles. Before invoking Python, a callback, a
finalizer-capable decref, or a Greenlet switch, code must end every:

- Bevy `World`, resource, entity, or query borrow;
- mutable or immutable compatibility `RefCell` borrow;
- GIL-runtime logical-state borrow;
- mutex or other guard;
- temporary Python borrowed reference; and
- temporary FFI slice, pointer view, or stack alias exposed to reentry.

Bevy Defer's scoped `WORLD` binding remains installed by
`run_async_executor` while the Future is polled. That binding is not itself a
derived `World` borrow. No compatibility code may carry a reference obtained
through it across a Greenlet switch.

### 5.2 The suspended `Future::poll` frame

The Phase 1 proof must include the actual poll signature conceptually in
scope:

```text
poll(self: Pin<&mut CarbonDriver>, cx: &mut Context<'_>)
```

When Greenlet switches into Python, the Rust poll stack is suspended. V5
therefore requires all of the following:

1. `Pin<&mut CarbonDriver>` covers only fields that reentrant Python cannot
   access or move.
2. No reference derived from `cx` survives the switch. If a wake is needed,
   clone its `Waker` into the stable wake cell first.
3. Reentrant Carbon calls operate on stable logical state, never through the
   suspended `&mut CarbonDriver`.
4. A driver-active token rejects nested polling before the executor or Future
   is touched.
5. The Greenlet/native bridge returns to the same switch call before that
   invocation of `poll` returns `Pending` or `Ready`.
6. No Greenlet may retain a continuation that can resume into a poll
   activation after that activation has returned.
7. The `App`, `World`, driver task, and Future cannot be destroyed while
   Python can return into the suspended poll stack.

If the Greenlet bridge requires a returnable continuation to outlive one
`poll` invocation, the selected architecture fails. Do not solve that failure
with an untracked raw pointer to the Future or `World`.

### 5.3 Reentrancy and no nested repoll

Within `ExecutingSegment`, nested Python calls invoke Carbon state-machine
operations directly and synchronously. They do not call `App::update`,
`run_async_executor`, `LocalExecutor::try_tick`, or `Future::poll` again.

Required behavior:

```text
driver poll
    -> Greenlet switch
        -> Python callback/tasklet
            -> nested scheduler.schedule()/channel operation
                -> direct Carbon transition and Greenlet return/yield
            <- nested operation
        <- Python
    <- original Greenlet switch
<- same driver poll
```

The driver-active token is owner-thread-only and generation-checked. A nested
entry with a different runtime generation, host, or thread fails before
mutation. A same-driver nested entry uses the active transition context.

### 5.4 Driver state machine

The minimum lifecycle is:

```text
Idle
  -> Requested
  -> ExecutingSegment
  -> Committing
  -> Idle

Idle or Requested
  -> ShuttingDown
  -> Dead
```

Additional rules:

- nested Carbon calls do not create a second lifecycle; they remain inside
  `ExecutingSegment`;
- shutdown requested during `ExecutingSegment` is recorded and deferred
  until the Greenlet returns and commit reaches a safe boundary;
- no new request is accepted after `ShuttingDown` begins;
- `Pending` may be returned only from an idle-safe point with no suspended
  Greenlet/native continuation into that poll frame; and
- `Ready` is returned only after manager cleanup, callback/owned-reference
  disposition, and wake deregistration are complete or explicitly classified.

### 5.5 Task-handle ownership and fail-stop Drop

The host uses Bevy Defer's public `AsyncExecutor::spawn_task` and retains the
returned `Task<()>`. It never uses `spawn_any`, `spawn`, or `detach` for
`CarbonDriver`. Dropping the handle cancels the Future and is not shutdown.

Headless thread state or an embedded non-`Send` App resource owns the handle.
Normal shutdown is:

1. mark the generation `ShuttingDown` and reject new requests;
2. wake the owner driver;
3. poll while `World`, executor, and host live;
4. perform Carbon teardown only at safe switch boundaries;
5. let the driver return `Ready` and atomically record `Dead`; and
6. only then release the Task and owner state.

The host sets `armed = true` immediately before spawning its driver Task. An
unarmed bootstrap may be dropped normally. An armed host may be dropped
normally only after `Dead`.

The experimental abnormal policy is fail-stop:

```text
Drop(host):
    if !armed or state == Dead:
        release normally
    else:
        emit a minimal non-allocating diagnostic
        abort the process without panic or unwind
```

Do not panic, attempt best-effort cleanup, cancel/detach the Task, or leak only
part of continuation state. Subprocess laws deliberately drop live `Idle`,
`Requested`, and safely constructible active-state fixtures and must observe
fail-stop termination before any driver-Future destructor runs.

This is an approved experimental host-safety divergence. Production may
replace it only with a proven whole-host mechanism retaining Task, executor,
Future, Greenlet/native continuation, manager, Python edges, generation, and
wake state as one ownership closure.

### 5.6 Wake protocol

The cross-thread wake object is independent of Python and Bevy owner state:

```text
Arc<WakeState> {
    requested: AtomicBool,
    waker: Mutex<Option<Waker>>,
    generation: atomic or immutable generation,
}
```

The exact lost-wakeup algorithm must be specified and tested before Phase 3.
At minimum:

- logical work is committed before `requested` is published;
- a foreign thread never stores a Python object, Greenlet, `World`,
  `LocalExecutor`, or `Rc` in the wake cell;
- `poll` clones/registers the current Waker without retaining `Context`;
- the requested flag is rechecked after registration;
- wake coalescing preserves at least one poll after every idle-to-runnable
  transition;
- stale-generation wakes are harmless; and
- the wake mutex is never held during Carbon mutation, callback invocation,
  decref, or Greenlet switching.

## 6. Threading and Rust sharing model

### 6.1 Supported experiment and thread matrix

The initial target is GIL-enabled CPython with one main interpreter.

| Deployment | Carbon-executing Python threads | Manager/host placement | Cross-thread Carbon channels |
|---|---:|---|---|
| Standalone experimental | Multiple | One manager + private headless host + driver per participating Python thread | Required; audited unchanged Scheduler tests are authoritative |
| Embedded experimental | Exactly one owner | One manager + one App driver on the bootstrap owner thread | Unsupported; foreign entry rejects before manager creation/mutation |
| Production embedded | Undecided | Requires a new topology decision | No support inferred from experiments |

Free-threaded CPython, active subinterpreters, post-init embedded attachment,
Greenlet migration, and embedded worker managers are unsupported. Detectable
unsupported configurations fail before manager creation. Production support
requires separate architecture and evidence.

### 6.2 GIL-gated logical runtime

V5 selects one concrete sharing strategy rather than saying only that the GIL
serializes behavior.

Process-visible Carbon logical state lives in a wrapper conceptually like:

```text
GilRuntimeCell<RefCell<LogicalRuntime>>
```

The wrapper may require a narrowly audited `unsafe impl Sync`, but it exposes
no unguarded reference. Every access requires a proven held-GIL token and a
closure. The token is obtained only at a CPython boundary that holds the GIL
or through a balanced `PyGILState_Ensure` path where that API is valid. Debug
builds assert `PyGILState_Check` at each access.

`LogicalRuntime` contains only state that may be inspected or changed under
the GIL, including:

- manager/tasklet/channel registries and generations;
- deterministic runnable and waiter links;
- process-global callback slots, timeout publication counters, and
  `useNestedTasklets`;
- standalone logical cross-thread runnable commitment; and
- `Arc<WakeState>` handles for owner notification.

No `RefCell` borrow from this cell survives a callback, Greenlet call, or a
decref that may run Python. Operations remove or clone the required owned
value while borrowed, release the borrow, and only then invoke user code or
release the Python reference.

### 6.3 Owner-only state

The following are owner-thread-only, non-`Send` state held in thread-local or
App non-send storage:

- headless `App`/`World` or embedded host handle;
- driver task handle and active transition token;
- Greenlet continuations and switch trampoline state;
- Bevy Defer `AsyncExecutor`/`LocalExecutor` relationship; and
- owner-thread Python invocation state.

Cross-thread code receives only logical IDs/generations and `Arc<WakeState>`.
It cannot dereference owner-only state.

### 6.4 Standalone cross-thread channel commitment

This protocol applies only when two standalone Python threads already own
valid managers/headless hosts. When rendezvous releases a tasklet owned by the
other manager:

1. under the GIL, perform match, packet transfer, waiter removal, balance
   update, and logical insertion into the owner manager's runnable structure;
2. release the logical-state borrow;
3. publish/wake through that manager's thread-safe wake cell; and
4. let the owner thread pump its headless host and switch Greenlet.

Logical commitment occurs at step 1. Before the owner pump, `getruncount`,
queue properties, and callbacks observe the released tasklet as the classified
standalone contract requires. Delaying insertion to a future pump is forbidden.

Experimental embedded mode has no foreign Carbon manager and never reaches
this protocol. Foreign embedded Carbon entry rejects before mutation or wake.

The GIL-gated cell replaces a new general channel mutex for this target. A
free-threaded design is a separate architecture with separate lock-order and
reentrancy proof.

## 7. CPython, Greenlet, C++ ABI, ownership, and GC

### 7.1 Selected FFI strategy

Before Phase 2, the implementation must pin and use low-level `pyo3-ffi` (and
only the minimum associated build configuration support) for CPython objects,
slots, argument parsing, pending exceptions, reference counts, and GC hooks.
Do not use high-level PyO3 type or module macros for the compatibility types;
they can obscure slot layout, borrowed/new-reference distinctions, and exact
exception timing required by the legacy contract.

A narrow C++ shim under `bevy_defer/carbon_compat/native/` will:

- include the unchanged `include/Scheduler.h`;
- include/use the supported Greenlet C API;
- construct the `SchedulerCAPI` table using the original C++ declarations;
- expose only the Greenlet and compiler/ABI operations Rust needs; and
- forward into panic-contained Rust entrypoints.

The same `PyInit__scheduler` implementation is linked into the standalone
extension and referenced by the embedded built-in registration path. Every
`extern "C"` entry catches Rust unwinding and translates it to the declared
Python/native error result. No panic crosses C, C++, CPython, or Greenlet.

### 7.2 Python surface

The standalone artifact is staged as `_scheduler` so the unchanged
`python/scheduler/__init__.py` imports it. Embedded mode registers the same
name as built-in and uses the same unchanged wrapper.

Preserve the full exported surface, including:

- module functions, names, parsing, results, and exceptions;
- `tasklet`, `channel`, and `schedule_manager` types;
- `TaskletExit` identity and inheritance;
- weak references, subclassing, iterators, callable setup, and invalid
  subclass errors;
- tasklet/channel properties and members not covered by common tests;
- `QueueChannel` and `block_trap` behavior from the unchanged wrapper;
- process-global callbacks, timeout counters, and nested-tasklet flag; and
- standalone import and teardown behavior.

Embedded entry restrictions are explicit host-extension behavior and must be
tested separately from standalone compatibility.

### 7.3 Native C++ capsule

The public header is C++-only. Preserve:

- capsule import name `scheduler._C_API`;
- the pointer stored in the capsule;
- `SchedulerCAPI` size, alignment, field order, offsets, signatures, and
  calling conventions;
- `PyTaskletType` and `PyChannelType` identity;
- each function's ownership and error convention; and
- `TaskletExit` as `PyObject **`, including `*TaskletExit` identity.

Do not compare opaque `PyCapsule` object bytes. For the experiment, compile
the unchanged native tests through an additive overlay. Production ABI proof
also needs independently frozen old layout constants and a precompiled legacy
consumer; recompiling consumer and provider from the same current header is
only source-compatibility evidence.

### 7.4 Boundary laws

- Make no Python C API call without the GIL.
- Invoke no Greenlet off its creating OS thread.
- Release no Python reference on a Bevy worker.
- Let no lock or logical-state borrow cross user code or finalizer-capable
  decref.
- Validate type, liveness, generation, wrapper-cleared state, manager, and
  owner thread before dereferencing every raw handle.
- Return success only with the intended pending-exception state; return an
  error only with the intended exception set.
- Concentrate unsafe code in FFI, Greenlet, capsule, callback, and the
  GIL-cell implementation.
- Document each unsafe block with the invariant that makes it sound and the
  test that attacks that invariant.

### 7.5 Ownership ledger

Before introducing each Python edge, record acquire, successful release,
replacement, rollback, `tp_clear`, and deallocation behavior. The ledger must
cover at least:

- Python thread-state dictionary to manager wrapper;
- manager to main tasklet and registered tasklets;
- Python wrapper to generational Rust handle;
- tasklet to callable, args, kwargs, Greenlet, parent, transfer object,
  pending exception, exception handler, and context-manager getter;
- runnable and channel-wait membership references;
- channel transfer/exception packets;
- global Python schedule/channel callback slots;
- native fast callback slot;
- module to types, exception, Greenlet state, and capsule;
- capsule to the static table and `PyObject **TaskletExit`; and
- logical manager record to `Arc<WakeState>` without extending Python object
  lifetime.

### 7.6 CPython cyclic GC

As soon as Rust owns a Python edge, `tp_traverse` and `tp_clear` must reach it
through an explicit low-level FFI protocol.

Traversal must visit every direct strong Python edge exactly once under the
GIL without allocation, mutation, user code, equality, hashing, repr, or
reference-count change. Clear must be idempotent, detach every cycle-forming
edge, and leave a safe tombstone for repeated clear/dealloc. Weakref clearing
must keep classified baseline timing.

GC support is implemented with each edge, not postponed after scheduler
behavior. Rust memory safety does not excuse leaked Python cycles.

### 7.7 Interpreter startup and finalization order

The same embedded owner OS thread performs bootstrap, `Py_Initialize`, driver
polling, and `Py_FinalizeEx`.

Normal embedded shutdown is:

1. reject new host submissions and Carbon entries;
2. request driver shutdown while CPython and the GIL are usable;
3. pump the App runner until the driver records `Dead`;
4. release the retained Task only after `Dead`;
5. clear managers and every explicitly clearable compatibility-owned Python
   edge while holding the GIL;
6. call `Py_FinalizeEx` while dead compatibility App/resources remain alive so
   module/type finalizers can release remaining edges;
7. mark the bootstrap finalized and prohibit every later CPython/Greenlet API
   call from Rust destructors; and
8. drop the now-dead compatibility resources and App.

No App/executor/driver destructor runs before step 6 if CPython finalizers can
consult its generation or host. No compatibility destructor decrefs or invokes
CPython after step 6.

Standalone mode does not own `Py_FinalizeEx`. Its module/free and per-thread
manager cleanup drive every armed headless host to `Dead` while CPython is
usable. A controlled embedded-CPython teardown probe verifies that ordering;
ordinary Python process-exit tests supplement it.

Any live armed host reaching destruction follows §5.5 fail-stop. Interpreter
finalization is never implicit Task cancellation.

## 8. Carbon compatibility state and transitions



### 8.1 Orthogonal tasklet axes

Do not model public tasklet state as one mutually exclusive lifecycle enum.
Store or derive these axes separately:

- wrapper valid/cleared;
- manager identity, generation, and owner thread;
- main-tasklet identity;
- callable bound and metadata present;
- Greenlet/continuation present;
- alive;
- paused;
- current;
- public scheduled flag;
- runnable-link membership and neighbors;
- channel blocked flag, direction, FIFO membership, and neighbors;
- transfer-in-progress and transfer packet;
- parent and first-run state;
- reschedule request and tagged removal;
- pending kill/control/exception state; and
- `times_switched_to`.

At minimum, the representation must support:

| State configuration | Bound | Greenlet | Alive | Scheduled | Runnable role | Paused |
|---|---:|---:|---:|---:|---|---:|
| Constructed/unbound | no | no | no | no | none | no |
| Bound dormant: `bind(callable)` | yes | no | no | no | none | no |
| Bound paused: `bind(...args...)` | yes | yes | yes | no | none | yes |
| Ready after setup/insertion | yes | yes | yes | yes | member | no |
| Active linked | yes | yes | yes | yes | member/current | no |
| Trapped paused run | yes | yes | yes | yes | member | yes |
| Channel blocked | operation-specific | yes | yes | operation-specific | transient/none | operation-specific |
| Main | no | yes | yes | yes | sentinel/current | no |
| Dead wrapper | implementation-specific | dead/none | no | no | none | no |

Main may appear in a channel send or receive wait queue while another tasklet
makes progress. `paused` and `scheduled` may both be true. These are valid
reachable compatibility states, not invariant violations.

### 8.2 Runnable-chain laws

The compatibility queue implements Carbon operations:

- insert at back;
- insert to run next;
- front-plus-one reschedule;
- remove a linked tasklet;
- select relative to current/base tasklet;
- snapshot the entry tail for targeted nested run;
- keep the selected tasklet linked while its Greenlet executes;
- remove it only after control returns to manager `Run`; and
- apply terminal cleanup, back reschedule, or front-plus-one reschedule after
  that return.

Public `next`, `prev`, cached run count, calculated run count, and ordering
must follow this representation. A clean internal “Running means no queue
membership” transition is not isomorphic to the baseline and is forbidden.

### 8.3 Bind, setup, run, switch, and nested-tasklet policy

These behaviors move together with their callable, parent, and exception
dependencies:

- `bind(callable)` stores callable/metadata without Greenlet creation,
  liveness, or insertion;
- bind with args/kwargs creates a Greenlet and marks alive/paused without
  insertion;
- setup requires a bound callable, creates/initializes the Greenlet, marks
  alive, and inserts;
- tasklet `run()` inserts a detached alive tasklet before traversal;
- a later switch-trap can therefore leave paused plus scheduled;
- tasklet `switch()` routes through manager `Run(this)` and parent/yield
  behavior, not a raw isolated Greenlet switch;
- parent assignment and rollback occur in the same control unit; and
- `TaskletExit`, `dont_raise`, normal exceptions, context manager, and
  exception-handler paths exist when the corresponding operation first moves.

The process-global `s_useNestedTasklets` equivalent is part of Phase 2, along
with `set_use_nested_tasklets`, `get_use_nested_tasklets`, and both branches of
`Tasklet::Run`. No phase may implement tasklet run while deferring that flag to
generic module-surface completion.

### 8.4 Schedule-callback ordering

For a same-thread switch to a different tasklet, preserve this observable
sequence at the operation-specific point:

1. complete validation that precedes the switch-trap check;
2. increment the target's `times_switched_to`;
3. update time-limited switched accounting through `OnSwitch` when applicable;
4. invoke the Python schedule callback with `(previous, next)`;
5. invoke the fast native schedule callback even if the Python callback left
   an exception pending, on the classified baseline path;
6. assign current to `next`; and
7. invoke the Greenlet continuation.

During the Python callback, `scheduler.getcurrent()` still observes
`previous`, while inspecting `next` sees the incremented switch count. Trace
events must represent these ordering points, not just one “current changed”
event.

Callback return values may be released safely rather than reproducing a
leak. Pending-exception timing, callback order, and whether control continues
are separately classified observable behavior.

### 8.5 Channel operation prefixes

`will_block` records whether an opposite waiter existed at callback entry. It
does not guarantee that the operation ultimately blocks. The callback may run
before later trap/closed validation or callback-induced reentrancy fails the
operation.

Send prefix:

1. observe whether a receiver exists;
2. invoke channel callback;
3. set current tasklet transfer-in-progress;
4. on unmatched send, perform current/trap/closed checks at baseline points,
   then acquire/link/store/yield or perform exact rollback; and
5. on match, pop oldest receiver, transfer packet, commit scheduling
   synchronously, and apply preference.

Receive prefix:

1. set current tasklet transfer-in-progress;
2. observe whether a sender exists and invoke channel callback;
3. on unmatched receive, acquire waiter reference, link into receive FIFO,
   and update balance;
4. perform block-trap and closed checks at baseline points with their rollback;
   and
5. on match, pop oldest sender, transfer value/exception, commit scheduling
   synchronously, and apply preference.

Send and receive intentionally differ. A shared “callback first, mutate
later” preflight is a new semantic and cannot be called parity.

### 8.6 Channels and blocked control are one unit

Move together:

- channel construction, active registry, weakrefs, iterator, queue, balance;
- send, receive, send-exception, and send-throw packets;
- preference and callback behavior;
- main and non-main blocking/deadlock behavior;
- kill, throw, pending kill, clear, close, open, global unblock, and teardown;
- cross-thread logical commitment and owner wake; and
- ownership/GC of waiters, packets, and links.

Exactly one component owns unlink, balance adjustment, packet release, waiter
reference release, and runnable insertion for every success, error, trap,
kill, close, and teardown path. Phase 3 may not depend on an unspecified
future kill/throw bridge.

### 8.7 Preference entrypoints

Keep Python and native setters distinct:

- Python assignment changes preference only for `-1`, `0`, or `1`; an
  ordinary out-of-range integer leaves the previous value unchanged.
- The native C++ setter clamps below `-1` to `-1` and above `1` to `1`.
- Python conversion overflow is a named defect boundary and must produce a
  safe, classified result.

One shared clamping Rust setter would break Python behavior.

### 8.8 Run budgets, counters, and nested runs

Experimental compatibility must:

- preserve main-only budget checks;
- preserve first-iteration progress for a zero time limit;
- preserve ambient manager run-mode interaction until a named divergence is
  approved;
- publish timeout counters through process-global fields;
- count baseline successful queue-removal/dequeue cycles rather than claiming
  terminal tasklet completion;
- avoid incrementing switched count when switch-trap returns before
  `SetCurrentTasklet`/`OnSwitch`; and
- characterize nested limited-run corruption before introducing a scope-stack
  repair.

A per-manager counter or automatically restored nested RunScope may be a
future safety/design improvement, but it is not strict parity.

### 8.9 Exact and partial-order contracts

Runnable order and each channel FIFO are exact deterministic contracts.
Operations based on baseline `std::unordered_set` iteration, including
unblocking unrelated active channels and destroying unrelated registered
tasklets, may have legitimately unspecified sibling order.

For such behavior compare:

- allowed final outcomes;
- exact order inside each individual queue/FIFO;
- required happens-before edges;
- exactly-once cleanup; and
- forbidden outcomes.

Do not invent one canonical total trace for unordered cleanup, and do not use
partial-order comparison to weaken deterministic Carbon queues.

## 9. Defects and approved divergence

### 9.1 Contract classes

Each touched behavior receives one of these classes:

| Class | Meaning | Required evidence |
|---|---|---|
| Exact compatibility | Deterministic public baseline behavior | Exact value, exception, state, callback, and order |
| Allowed outcomes | Publicly permitted nondeterministic sibling order | Outcome set plus partial/happens-before order |
| Approved safety repair | Memory-safety, UB, leak, or nontermination repair | Explicit old/new expectation and regression |
| Host extension | New standalone/embedded host behavior | Extension test plus compatibility-off invariance |
| Unsupported | Outside the experimental target | Early deterministic rejection without mutation |

“Legacy defect” is not a normalization bucket. Every difference must name the
operation, old observation, new observation, reason, and acceptance test.

### 9.2 Seed defect register

The experiment does not need a complete historical audit before the headless
probe. A named decision is required before implementing any intersecting row.

| Area | Baseline issue/candidate | Initial policy |
|---|---|---|
| Worker-thread tests | Some `assertRaises` calls evaluate before the assertion | Retain original test and add a reliable probe |
| Native tests | Suspicious stolen-reference tuple cleanup | Retain original and add audited native ownership probe |
| `switch_trap` parsing | Continues after parse failure with invalid delta | Deterministic error/no mutation; approved safety repair |
| Callback setter return | Previous callback may be decref'd before return | Return an owned live object with same identity |
| Callback setter ownership | Python and native setters have different expectations | Preserve entrypoint-specific contracts |
| Callback calls | Successful callback return objects can leak | Release safely while preserving call/error order |
| Parent assignment | Failure paths can leak parent/main references | Balance all paths; preserve visible parent result |
| Closed receive | Waiter reference rollback is asymmetric | Balance safely; preserve public error/queue/balance result |
| Duplicate run-next | Reference acquired before already-scheduled detection | Characterize reachability and balance ownership |
| Tasklet handler | Getter/destructor ownership is suspicious | Safe getter and destructor with identity preserved |
| Tasklet GC | Baseline traverse/clear omits owned edges | Complete traversal/clear for new ownership graph |
| Callable wrapper | Enter/handler/exit temporaries can leak | Release safely, preserving call/error order |
| Manager creation | Thread-dictionary failure can double release | Fault-inject before production promotion |
| Module state | Greenlet import state has no explicit teardown | Document retention or implement balanced teardown |
| Send failure | Transfer flag can remain set after early failure | Characterize; preserve only if observable contract requires it |
| Nested limited run | Inner run can corrupt outer ambient budget | Preserve experimentally or approve named repair after probe |
| Teardown | Tasklet catching `TaskletExit` can prevent termination | Define bounded safety policy as explicit divergence |

Memory corruption, dangling references, double release, uninitialized reads,
and unbounded teardown are not compatibility goals. Observable safe behavior
around them still needs an explicit decision.

## 10. Evidence and test strategy

### 10.1 Two milestones

The roadmap has two separate acceptance levels:

1. **Experimental backend:** opt-in implementation builds, uses the selected
   Bevy Defer path, passes the unchanged Scheduler Python/native suites and
   Carbon I/O on the supported environment, and makes no production-equivalence
   claim.
2. **Production backend:** complete contract, differential, ABI, ownership,
   sanitizer, platform, performance, and rollout evidence.

Production certification is not a prerequisite to learning from the vertical
slice. Conversely, passing the experiment does not prove production parity.

### 10.2 Evidence authority

For a deterministic public behavior, prefer:

1. a reliable unchanged test that actually observes it;
2. control flow in the pinned legacy implementation;
3. a focused reliable black-box probe;
4. public documentation; and
5. comments.

All original tests remain mandatory gates, but known broken assertion forms
or suspicious reference handling are not unquestioned semantic authorities.
Keep them unchanged and add a reliable probe below `bevy_defer/`.

### 10.3 Property-first laws

Tests and laws for a phase must be committed before or with the behavior they
govern and then remain immutable except for a separately reviewed contract
correction.

For new Python-visible behavior:

- use Hypothesis strategies rather than only handpicked examples;
- retain fixed regressions with `@example` or `st.just` where useful;
- preserve minimized counterexamples as permanent regressions; and
- use `RuleBasedStateMachine` once temporal tasklet/channel/driver behavior is
  introduced.

Structural link, compile, ABI-layout, panic-boundary, and native lifetime
checks remain Rust/C++ executable tests; Hypothesis does not replace a linker
or sanitizer. Phase 0 does not require a complete state machine before any
implementation. Focused properties grow with the touched slice.

Maintain two invariant sets:

- **legacy oracle laws**, which permit reachable baseline combinations and
  approved nondeterminism; and
- **target safety laws**, which express new Rust/host guarantees.

Never run target-only clean-state invariants against legacy and call the
result a parity failure.

### 10.4 Non-interfering traces

Full differential tracing begins only after the vertical architecture works.
Test instrumentation must:

- use numeric/generational IDs instead of strong Python references;
- never call repr, equality, hashing, descriptors, finalizers, or user code;
- retain no object beyond its baseline lifetime;
- use sequence numbers, not wall-clock order;
- add no transition-path I/O or lock order; and
- be fully disabled without changing decisions.

Send and receive require distinct event prefixes. Unordered cleanup uses a
partial-order comparator. Trace non-interference is itself a testable law,
including refcount, weakref, GC, and destruction-order comparisons with
tracing on and off.

### 10.5 Reproducible build/test overlay

The additive package harness:

- verifies `environment.lock.toml` before build;
- requires tracked `bevy_defer/Cargo.lock` and rejects lock drift;
- runs Cargo metadata/tree/build/test with `--locked`;
- builds exactly one of `standalone` or `embedded` and records its feature graph;
- builds into a private staging directory;
- stages only the extension plus unchanged root `python/` for standalone;
- excludes every extension artifact and verifies built-in origin for embedded;
- sets `PYTHONDONTWRITEBYTECODE=1` for read-only Python sources;
- compiles unchanged native tests with unchanged headers;
- stages an experimental Scheduler description for Carbon I/O; and
- writes output only under `bevy_defer/target/` or temporary storage.

A clean-checkout reproduction fails rather than regenerate a lock or silently
select another toolchain/dependency graph.

### Phase 1A — Disposable standalone headless feasibility probe

Purpose: prove cheaply that a Greenlet segment runs inside Bevy Defer's real
owner-thread executor context.

Actions:

1. Add one workspace member and the exact feature/crate-type policy in §4.1.
2. Build/test only `--no-default-features --features standalone --locked`.

Phase 1B requires separate authorization after review.

### Phase 1B — One-process embedded topology and continuation proof

Purpose: prove the corrected bootstrap, singleton, and continuation architecture
in one process.

Build one real executable with
`--no-default-features --features embedded --locked` that:

1. links the rlib exactly once and excludes the extension from package/module
   search paths;
2. on the owner OS thread, verifies CPython is not initialized;
3. constructs a real App and fresh `EmbeddedRuntimeBootstrap`;
4. adds `CarbonCompatPlugin::run_in(...)` with that bootstrap;
5. proves the plugin installs one runner/driver and registers

6. only then calls `Py_Initialize` on the same owner thread;
7. imports unchanged `scheduler` and observes `_scheduler` as built-in;
8. compares bootstrap/plugin/Python runtime generations;
9. submits initial Python through the exact App driver;
10. runs through that App's Bevy Defer executor on the owner thread;
11. performs nested schedule/yield without recursive executor polling;
12. rejects external/foreign Carbon entry before manager creation or mutation;
13. exercises an ordinary Bevy Defer Future before/after the Carbon segment;
14. requests shutdown at safe/reentrant points and reaches `Dead`;
15. releases Task, clears legal Python edges, calls `Py_FinalizeEx`, and only
    then drops dead App/resources; and
16. separately proves armed non-`Dead` App teardown aborts fail-stop.

The fixture fails on post-init plugin attachment, non-built-in origin, a
discoverable/loaded extension, mismatched generations, a second runner/plugin,
or wrong-thread Carbon execution. `PYTHONPATH` precedence is not a singleton
mechanism.

Safety review covers:

- `Pin<&mut CarbonDriver>` and every field;
- `Context<'_>` and Waker cloning/registration;
- suspended Rust/C++/CPython/Greenlet frames;
- nested-entry exclusion from repoll;
- App/World/executor/Task/bootstrap ownership;
- every normal/fail-stop lifecycle state; and
- every CPython call/decref before versus after `Py_FinalizeEx`.

Exit:

- normal/debug builds prove one compatibility runtime;
- plugin/bootstrap attachment and built-in registration precede CPython init;
- entry, runner ownership, and owner thread are proven;
- reverse driver/CPython/App teardown passes;
- abnormal teardown follows fail-stop;
- the FFI strategy creates/tears down the minimal module safely;
- lock/environment evidence remains unchanged; and
- Phase 1A and root Bevy Defer tests remain green.

Failure blocks Phase 2. Separate headless/App tests cannot replace this gate.

## 13. Experimental Definition of Done

The backend is ready for an opt-in experimental PR only when:

- all changed paths are under `bevy_defer/` and deletion counts are zero;
- root Bevy Defer source/defaults and original tests remain unchanged;
- exact environment verification passes and tracked `Cargo.lock` is unchanged
  by every `--locked` command;
- exactly one mode is enabled per build;
- standalone packaging contains the extension deployment only and embedded
  packaging contains no loadable `_scheduler` extension;
- one package depends directly on root Bevy Defer;
- the embedded process proves bootstrap/plugin/module identity;
- plugin attachment and built-in registration precede CPython init;
- the plugin owns one executor run and does not rely on `CoreAsyncPlugin` to
  poll;
- all drivers use Bevy Defer's owner-thread runner path;
- embedded Python begins through the driver and foreign/external Carbon entry
  fails before manager creation/mutation;
- standalone multi-thread tests use one manager/headless host per thread and
  commit logical release before wake;
- nested Carbon never recursively polls the executor;
- poll-frame/Greenlet safety tests pass;
- each host retains its Task and reaches `Dead` before release;
- armed non-`Dead` Drop is proven fail-stop;
- embedded teardown reaches `Dead`, legally clears Python edges, finalizes
  CPython, then drops App;
- GIL-gated logical and wake state obey documented invariants;
- low-level `pyo3-ffi` plus unchanged-header C++ shim provide boundaries;
- unchanged Python imports the opt-in `_scheduler`;
- all Scheduler Python tests pass unchanged individually/together with only
  baseline skips;
- all native C++ tests compile/pass unchanged;
- complete Carbon I/O tests pass;
- root Bevy Defer tests pass;
- selected local-fork tests pass if selected/touched;
- no known wrong-thread switch, FFI panic escape, lost waiter/wake, untraversed
  Python edge, or dangling poll continuation remains; and
- documentation calls the backend experimental, not production-equivalent.

## 14. Production Definition of Done

Production compatibility additionally requires:

- every public Python, native, standalone-host, and embedded-host operation
  classified;
- every reliable historical test and replacement probe passing;
- exact and allowed-partial-order contracts passing separately;
- zero unexplained differential mismatch;
- complete callback, exception, ownership, reentrancy, metric, and
  cross-thread visibility evidence;
- complete GC traversal/clear and teardown evidence;
- independent frozen `SchedulerCAPI` constants and precompiled old consumers;
- supported OS/compiler/Python/Greenlet matrix coverage;
- explicit decisions for interpreter attachment, subinterpreters, and
  free-threaded Python;
- no unclassified panic, UB, double release, stale handle, leak, deadlock,
  lost wake, dangling continuation, or nontermination path;
- approved latency/throughput/memory budgets;
- representative production Carbon workloads;
- an external packaging and rollout plan selecting the backend before import;
  and
- demonstrated rollback to the legacy artifact.

Legacy source removal is not part of this roadmap.

## 18. Final recommendation

After separate code authorization, complete Phase 0's enforceable
reproducibility gate, implement Phase 1A, publish its evidence, and stop.

Only a separate authorization may begin Phase 1B. That proof now has one exact
startup order—bootstrap/plugin/inittab before CPython—and one inverse teardown
order—driver `Dead`, Task/Python cleanup, `Py_FinalizeEx`, then App drop. It also
has a selected fail-stop policy and exact embedded artifact mode.

A green Phase 1B unlocks Phase 2. Phase 3 preserves baseline multi-thread
channels in standalone mode with one headless host per Python thread; the
experimental embedded backend remains deliberately single-owner. Any future
embedded multi-manager support requires a new production topology decision.

V5 therefore closes every blocking item in `report-v4.md` without widening the
implementation tree or starting code. If the locked Phase 1A or one-process
Phase 1B evidence falsifies the architecture, stop and revise the roadmap rather
than implementing API breadth on an unsound host.
